# 规则表（退款）

> 用途：把 C 出口要执行的判定与计算写成**可逐条实现、可逐条验收**的表。
> 上游：[数据与知识库设计](../../../../ai-learning-notes/项目迭代/电商客服-数据与知识库设计.md) §六、
> [状态机与工具契约](../../../../ai-learning-notes/项目迭代/电商客服-状态机与工具契约-草案.md)
> 状态：已确认（2026-11-02）
>
> **判定改由模型执行后，本表有两个用途**：
> 1. 作为 `judge` 的 prompt 依据（人话版规则）
> 2. 作为 `compliance` 的**独立复算**实现（代码版规则）——两者不一致即转人工


## 一、规则从哪来：三分类

| 来源 | 含义 | 能不能改 |
|---|---|---|
| **法定** | 法律/部门规章规定 | ❌ 不能，照抄 |
| **平台** | 我们自己定的，但**已经写进 `data/kb/` 且会被引用给用户** | ❌ 不能，改了要同步语料 |
| **自定** | 纯业务选择，语料里没有 | ✅ 可改，但要写清理由 |

**硬约束：规则表与语料不能冲突。**

语料是给用户看的、会被知识出口引用进答案。如果知识出口说「退货运费由商家承担」，
而 C 出口算出来扣了运费，用户拿两句话对质，系统就崩了。

## 二、退款流程的输入与输出

### 需要的输入

| 字段 | 现在有吗 | 说明 |
|---|---|---|
| 订单号 | ✅ `orders.id` | |
| 订单状态 | ✅ `orders.status` | 6 种状态 |
| 实付金额 | ✅ `orders.amount` | 分；已扣优惠 |
| 下单时间 | ✅ `orders.created_at` | |
| 发货时间 | ✅ `orders.shipped_at` | |
| **签收时间** | ❌ **缺** | 法规要「自签收次日起算」，没有这个字段算不出窗口 |
| **件数** | ❌ **缺** | 没有件数只能整单退，退不出「部分退款」 |
| 退款原因 | ❌ 由 `extract` 抽取 | 质量问题 / 无理由 / 其他 |

### 输出

| 字段 | 说明 |
|---|---|
| `eligible` | 可退 / 不可退 / 需人工 |
| `refund_amount` | 退款金额（分） |
| `reason_code` | 不可退时的原因码（给话术用） |

## 三、资格判定（不涉及金额）

按**顺序**判定，第一条命中即返回——顺序本身就是规则的一部分。

| # | 条件 | 结论 | 来源 |
|---|---|---|---|
| 1 | 状态 = 待付款 | ❌ 未支付，无需退款 | 自定 |
| 2 | 状态 = 退款中 | ❌ 退款处理中，不可重复申请 | 自定 |
| 3 | 状态 = 已关闭 | ❌ 订单已关闭 | 自定 |
| 4 | 状态 = 待发货 | ✅ 可取消，全额退 | 自定 |
| 5 | 状态 = 已发货、未签收 | ❌ 需签收后申请（或拒收） | 自定 |
| 6 | 商品属于**法定一律不适用**类（定作 / 鲜活易腐 / 拆封音像与软件 / 报刊） | ❌ 不适用无理由退货 | **法定**（第六条） |
| 7 | 商品属于**第七条三类**（拆封影响安全健康 / 激活试用后贬值 / 明示临期或有瑕疵），且平台已在下单页提示 | ❌ 不适用无理由退货 | **法定**（第七条）+ **平台**（下单页确认） |
| 8 | 商品不完好（剪吊牌 / 穿出门外 / 残留食物 / 受污受损） | ❌ 视为不完好 | **法定**（第九条）+ **平台**（returns.md:34-39） |
| 9 | 签收超过 7 个自然日 | ❌ 超出无理由退货期 | **法定**（第十条） |
| 10 | 以上都不命中 | ✅ 可退 | — |

**第 7 条的商品清单从哪来**：目前只明确了「奶瓶、奶嘴等入口喂养用品」（`returns.md:25`）。
其余品类（如电动吸奶器、婴儿监护器）语料未写，**按"未明确即不适用第 7 条"处理**——
宁可放行，不擅自扩大不可退的范围。

> 第 7 条曾经拆成两行（一条讲法规、一条讲奶瓶），实际奶瓶只是该条的一个实例。
> 合并后避免两处独立维护、说法不一致。

**注意第 7 条**：法规说的是"经消费者确认**可以不**适用"，没说"必须不适用"。

我们对这条的处理是**把确认前置到下单页**：该类商品（含拆封奶瓶）在结算页有明确提示，
勾选同意才可下单——因此**所有订单都视为"购买时已确认"**，规则可以无条件执行。

**为什么不在数据库里存这个标记**：它是平台级的前置流程（勾选项不可跳过），
不存在"没勾也能下单"的情况，存一个恒为 true 的字段没有信息量。

> 这一步是对语料的一次修正：原文写的是无条件的「一经拆封即不支持」，
> 比法规要求的更严。补上"下单页已提示、勾选即视为确认"后，规则与第七条对齐。

## 四、金额计算

### 4.1 可退金额

```
退款金额 = floor(实付金额 × 退货件数 / 总件数)
```

| 情形 | 计算 | 说明 |
|---|---|---|
| 待发货取消 | `amount` | 整单取消 |
| 整单退货 | `amount` | |
| 部分退货 | `floor(amount × n / quantity)` | 按件均摊 |
| 质量问题 | `amount`（同上） | **不退运费，也不额外赔运费** |

### 4.2 运费怎么处理

| 情形 | 谁付寄回运费 | 影响退款金额吗 |
|---|---|---|
| 质量问题 | 商家承担来回 | ❌ 不影响（退款仍是商品实付） |
| 七日无理由 | 消费者承担 | ❌ 不影响 |
| 运费险 | 赔付上限 12 元 | ❌ 不进退款计算（保险赔付另算） |

**简化**：运费不参与退款金额计算。理由是我们订单表里**没有运费字段**（`amount` 是商品实付），
加运费要连带改下单流程。这条写进决策记录。

### 4.3 优惠券怎么处理

| 情形 | 券 | 钱 |
|---|---|---|
| 整单退款 | 券退回（未过期） | 退实付 |
| 部分退款 | **券不退回**（语料 promo.md:31） | 按件均摊实付 |

**注意**：语料已经写了「部分退款券不退回」——计算规则必须遵守，否则又是一处冲突。

## 五、数据缺口（阻塞项）

这三条不补，上面的规则一半落不了地。

| # | 缺什么 | 为什么必需 | 建议 |

## 七、怎么验收

**手算 10 份合同对拍**（L3）——这是 C 出口唯一的硬指标。

| # | 合同要点 | 期望 |
|---|---|---|
| 1 | 已签收 3 天、完好、无理由 | 可退，退全额 |
| 2 | 已签收 8 天、无理由 | 不可退（超期） |
| 3 | 已签收 8 天、质量问题 | 可退（质量问题不受 7 天限制） |
| 4 | 定作商品 | 不可退 |
| 5 | 已拆封奶瓶 | 不可退 |
| 6 | 剪了吊牌 | 不可退（不完好） |
| 7 | 待发货、要取消 | 可退全额 |
| 8 | 已发货未签收、要退 | 不可退（需签收后） |
| 9 | 2 件退 1 件 | 退一半（floor） |
| 10 | 退款中的订单再申请 | 不可退 |

**"手算"的意思**：每条合同自己算出金额写进 JSON，代码算出来的必须一样。
不一致时**先怀疑代码，再怀疑手算**——手算也可能错。
