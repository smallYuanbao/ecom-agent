# 电商客服 Agent · 数据飞轮设计

> 状态：设计稿（2026-10-27）
> 上游：[意图与出口设计](./电商客服-意图与出口设计.md) · [数据与知识库设计](./电商客服-数据与知识库设计.md)
> 原则：**最小闭环——落池、审核、补库验证；不做自动写回与实时处理。**

---

## 一、五个部件

```
① 入口      低置信兜底 / 用户点踩 / 规则冲突转人工
              ↓
② 落池      一张表：问题 + 来源 + 信号 + 召回快照
              ↓
③ 归一化    同义问题合并（LLM 打标 + 相似度去重）
              ↓
④ 审核      列表页：通过 / 驳回 / 改写
              ↓
⑤ 写回      写进独立 FAQ 表，标记来源与审核人
              ↓
      （回到 ①，并用评测验证效果）
```

| 部件 | 职责 | 最小实现 |
|---|---|---|
| ① 入口 | 捕获"系统答不好"的时刻 | 兜底节点写库 + 点踩接口 |
| ② 落池 | 结构化留存证据 | 一张表（见 §三） |
| ③ 归一化 | 把同义问题合并 | 批处理脚本 + LLM + embedding |
| ④ 审核 | 人工确认要不要补 | 一个列表页 + 三个按钮 |
| ⑤ 写回 | 进入检索范围 | 独立 FAQ 表，检索时合并 |

**④ 不能省。** 没有人工确认的飞轮，等于让模型自己教自己。

---

## 二、三个入口

| 入口 | 触发时机 | `source` 标签 | 记录什么 |
|---|---|---|---|
| **低置信兜底** | A 出口证据不足 | `retrieval_low_conf` | 置信度信号 + 召回快照 |
| **用户负反馈** | 用户点踩 / 反馈"没解决" | `feedback` | 会话 id + 该轮证据 |
| **规则冲突** | C 出口守卫触发转人工 | `rule_conflict` | 触发的规则 id + 中间结果 |

**优先级**：`feedback` > `rule_conflict` > `retrieval_low_conf`
（用户主动说"不对"的样本质量最高；低置信里混着大量本来就不该答的问题）

## 三、表结构

```sql
CREATE TABLE low_conf_questions (
  id            INTEGER PRIMARY KEY,
  question      TEXT NOT NULL,          -- 原始问法
  normalized    TEXT,                   -- 归一化后的标准问题
  source        TEXT,                   -- retrieval_low_conf / feedback / rule_conflict
  reason        TEXT,                   -- 置信度 + 信号快照
  retrieved     JSON,                   -- [...] / [] / null 三态
  status        TEXT DEFAULT 'pending',  -- pending/merged/approved/rejected/written_back
  merged_into   INTEGER,                -- 合并到哪一条
  occurrence    INTEGER DEFAULT 1,      -- 出现次数（合并时累加）
  kb_ref        TEXT,                   -- 写回后的 FAQ 条目 id
  created_at    DATETIME,
  reviewed_at   DATETIME
);
```

**`retrieved` 三态语义**（与兜底一致）：

| 值 | 含义 | 审核时该怎么做 |
|---|---|---|
| `[...]` | 有召回但分低 | 看召回内容，可能只是阈值问题 |
| `[]` | 零命中 | 真缺知识，优先补 |
| `null` | 没走检索 | 不是知识问题，不该进补库队列 |

## 四、批处理流程

```
取 status='pending' 的条目（游标）
  → 串行逐条处理（不并发，保证同批同义问题能互相关联）
  → LLM 输出 {normalized, matched_id, suggested_answer}
  → embedding 二次校验相似度（≥0.9 视为同义）
  → 命中已有条目：occurrence += 1，status='merged'，merged_into=id
  → 未命中：写入 normalized，状态仍为 pending，等人工审核
  → 解析失败 / 返回不存在的 id：跳过 + 告警，游标不动，下轮重试
```

### 五个必须遵守的规则

| 规则 | 原因 |
|---|---|
| **游标 = status='pending'** | 处理完改状态，天然幂等，可重跑 |
| **串行逐条** | 同批第二条同义问题能命中第一条刚建的行 |
| **LLM 归一化 + embedding 校验** | LLM 会漏判，相似度兜底 |
| **驳回即终审** | 否则同一问题反复进队列 |
| **解析失败不推进游标** | 不吞错，下轮重试 |

## 五、审核页（最小实现）

**列表字段**：问题 / 来源 / 出现次数 / 召回快照 / 建议答案 / 状态

**三个操作**：

| 操作 | 结果 |
|---|---|
| **通过** | 写入 FAQ 表，状态 → `written_back` |
| **驳回** | 状态 → `rejected`（终审，不再入队） |
| **改写后通过** | 人工修改答案后写入 |

**一条建议**：审核页把 `retrieved` 三态显示出来——`[]` 的条目直接标红，提示"这是知识库缺失"。

## 六、写回策略

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 直接改知识库文档 | 单一来源 | 污染文档版本，难回滚 |
| **B** | **独立 FAQ 表** | 可回滚、可整表停用 | 检索时要合并两个来源 |

**选 B。**

检索时把 FAQ 表也纳入（作为第三个 collection 或同一索引的不同 source 标签）：

```
检索源 = 知识库文档 chunks + 法规 chunks + FAQ 表
```

**好处**：出问题可以整表回滚，不动源文档。

## 七、怎么证明它有效（最值钱的部分）

飞轮最大的问题是"看不出效果"。用 EvalFlow 量出来：

```
第 1 步：跑一次评测（补库前），记录 hit@3 / 覆盖率 / 拒答率
第 2 步：从低置信池挑 10 条，审核后补进 FAQ 表
第 3 步：用同一批题再跑一次（dataset_hash 必须一致）
第 4 步：对比指标
```

**预期结果**：

| 指标 | 补库前 | 补库后 |
|---|---|---|
| hit@3 | 0.62 | 0.85 |
| 覆盖率 | 0.70 | 0.88 |
| 拒答率（库外题） | 保持 | 保持（不该被补库影响） |

**最后一行是自检**：如果补库后库外题的拒答率也变了，说明补的内容污染了边界。

**这条对比是别人给不出的证据**：它同时证明飞轮在转、知识在长、评测能驱动迭代。

## 八、四个决策

| # | 决策 | 选项 | 选择 | 理由 |
|---|---|---|---|---|
| F1 | 处理方式 | 实时 / **批处理** | 批处理 | 逻辑简单、可重跑、不增加在线延迟 |
| F2 | 去重策略 | 关键词 / **LLM + embedding** | LLM 归一化 + 相似度二次校验 | 纯 LLM 会漏判 |
| F3 | 写回位置 | 知识库文档 / **独立 FAQ 表** | 独立表 | 可回滚，不动源文档 |
| F4 | 驳回后 | 可复活 / **终审** | 不复活 | 否则同一问题反复入队 |

## 九、不做的事

| 不做 | 原因 |
|---|---|
| **自动生成答案并写库** | 没人审的"AI 教 AI"，错误会累积 |
| **实时入队** | 每条兜底触发一次模型，成本与复杂度都上去了 |
| **多级审批 / 角色权限** | 单人项目没有意义 |
| **自动触发重训 / 重索引** | 补库后手动跑评测即可 |

## 十、与参考项目的差异

| 维度 | 参考实现 | 本设计 |
|---|---|---|
| 入口 | 三个（拒答/点踩/自评未过） | 三个（低置信/点踩/规则冲突），**带优先级** |
| 归一化 | LLM 一次输出标准问题 + 候选 id | 同思路 + **embedding 二次校验** |
| 写回 | 写知识库 | **写独立 FAQ 表**（可回滚） |
| 驳回 | 不复活 | 同左 |
| **验证** | 无 | **补库前后同批题对比** |

**最后一行是关键差异**：它的飞轮是"设计出来的闭环"，我们的是"被数据验证过的闭环"。
