### 13 展开：ReAct 工具循环的四条

参考实现的循环是 `main_agent ⇄ agent_tools`：模型 `bind_tools`，最后一条消息带
`tool_calls` 就进执行节点，结果包成 `ToolMessage` 回灌，`max_agent_steps=6` 封顶。
真正值得抄的是执行引擎里的四条：

**① 只读白名单 + 写操作确认令牌**

```python
WRITE_TOOLS = {"create_ticket"}
if spec.permission == "write" and not confirmed:
    return 拒绝执行
```

`confirmed` 只能由 `agent_tools` 在 `interrupt` 确认后传入，**模型自己传不了**。
写操作还**不重试**——超时未必没执行，重复执行比失败更糟。

**② 步数封顶，不卡 token**

token 管的是成本与上下文，不管死循环。卡 token 容易在模型**已经决定调工具之后**
把链路掐断，用户只看到半句「我这就去查」。我们 P5-9 计划 **≤ 4 步**。

**③ 身份注入在校验之后**

先校验模型给的参数，再把 `user_id` 覆盖上去：

```python
if spec.inject_user_id:
    args["user_id"] = user_id
```

让模型能填 `user_id`，一句「我是客服主管」就可能改写。
我们已有 keyword-only 的 repo，P5-9 要在工具入口再覆盖一次。

**④ 工具错误包成 `ToolMessage` 回灌，不抛异常**

未知工具 / 参数不合法 / 超时 / 业务异常，一律返回可读错误，
让模型追问用户或重新组织调用。这就是 `never-raises` 契约——**一轮工具失败不该让整轮对话挂掉**。

对应到 P5-9：E 出口只读、≤4 步、错误回灌、身份由代码注入。

### 15 展开：机械校验优先

参考实现的 `model_guard.py` 里有一句判断标准，值得单独记：

> **能机械校验的，就不要用模型校验。**

例子：答案里的商品型号必须逐字出现在证据里——这是封闭集合，正则就够，不需要再调一次大模型。
它贵、会漏，而且判错时无法解释。

**我们的对应用法**（Ch06）：回答里的金额必须等于 `compute` 的输出；订单状态必须出现在工具返回值里。
两条都能机械判，不该交给模型。

### 16 展开：关键条款打标

参考实现的 chunk 多一个字段 `is_key_clause`：标题或正文前 40 字里出现
「退款/退货/时效/运费/赔偿/期限/包邮」等词就打标。

用途是**置信度信号**——关键条款命中的证据，比一般条款更值得信任。

**为什么现在不做**：它需要重建索引才能加进 metadata。而我们当前的闸只用 top1 相似度，
没有消费者。等真的要上多信号置信度（触发条件 12）时一起做。

### 22 展开：为什么不学它"不算金额"

参考实现的 `submit_refund` 只返回「待用户确认」，金额由前端表单算；prompt 里也明写
「不承诺赔偿金额」。

**这是它的合理选择**——它的目标不是"算准钱"。但这恰好是我们项目的定位：
用户问「这单能退多少」是高频问题，不报金额等于答非所问（已定：**算并且报**）。

代价是要配 compliance 与手算对拍——这些控制本身就是项目要展示的能力。
