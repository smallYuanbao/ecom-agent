# 电商客服 Agent · 数据与知识库设计

> 状态：设计稿（2026-10-26）
> 上游：[意图与出口设计](./电商客服-意图与出口设计.md)
> 原则：**数据量 = 意图覆盖 × 边界密度**，不是"资料有多少"。

---

## 一、数据分四层，来源不同

| 层 | 放什么 | 来源 | 规模 |
|---|---|---|---|
| **知识库** | 政策、商品参数、会员、活动 | 真实法规 + 自造平台细则 | 6 篇 / ~5.6KB |
| **业务库** | 订单、物流、库存、优惠券 | 合成 | 每表 5–20 条 |
| **规则表** | 退款、价保、变更的判定条件 | 自定 | 3 组规则 |
| **对话语料** | 问法参考（不进库） | 公开数据集提炼 | 不复制 |

**12 个意图里只有 4 类需要知识库**：政策问答、商品规格、优惠券活动、会员权益。
订单/物流/库存走业务库，退款/价保/变更走规则表，投诉/闲聊不需要数据。

---

## 二、知识库：6 篇文档

| 文档 | 字数 | 支撑意图 | 必须写清的边界 |
|---|---|---|---|
| `returns.md` 退货退款 | ~1200 | 政策问答 | 不适用商品、完好标准、7 天起算点、赠品一并退 |
| `shipping.md` 运费配送 | ~800 | 政策问答 | 包邮门槛、偏远地区、运费险、超时赔付 |
| `invoice.md` 发票 | ~600 | 政策问答 | 电子/纸质、专票条件、30 天期限 |
| `member.md` 会员积分 | ~800 | 会员权益 | 三档等级、折扣、免邮次数、积分规则 |
| `promo.md` 优惠券活动 | ~700 | 优惠券活动 | 叠加规则、使用门槛、过期、退款后券退不退 |
| `products.md` 商品规格 | ~1600 | 商品规格 | 6 个 SKU（3 系列 × 2 型号）的参数 |

**合计约 5.6KB。** 比参考项目（14KB）更小，但边界密度更高。

### 每篇文档的写法要求

1. 用 `##` 分节，标题即切分点
2. 每节至少 1 个边界条件（"除了…""超过…""需先…"）
3. 写清"本文档不提供什么"（避免模型编数字）
4. 数字必须具体（几天、几元、几次），不要写"若干"

## 三、法规：只取 5 条，不取全文

来源：《网络购买商品七日无理由退货暂行办法》（2020 修订版）
- gov.cn：https://www.gov.cn/zhengce/zhengceku/2020-11/03/content_5557118.htm
- 市场监管总局：https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2023/art_26ca8fe29e184edd899fa0a7a060d935.html

| 条款 | 内容要点 | 支撑什么 |
|---|---|---|
| 第六条 | 定作、鲜活易腐、拆封音像/软件、报刊 → **不适用** | 拒答 / 边界 |
| 第七条 | 拆封影响安全健康、激活即贬值、临期瑕疵 → **经确认可不适用** | 条件判断 |
| 第八条 | 商品完好标准；**查验性开箱不影响完好** | 边界解释 |
| 第十条 | 七日**自签收次日**起算 | 时间计算 |
| 第十二条 | 赠品（含积分、代金券、优惠券）**一并退回** | 多要素 |

**约 2000 字，覆盖全部核心边界。** 剩余 25 条（法律责任、附则）对本项目无价值。

**合规依据**：《著作权法》第五条规定，法律法规、国家机关的决议决定命令不适用著作权法。政策文本可引用，需注明出处。

## 四、商品：6 个 SKU（3 系列 × 2 型号）

> 完整参数草案见 [商品规格草案](./电商客服-商品规格草案.md)

| 系列 | 型号 A | 型号 B | 交叉点（考点） |
|---|---|---|---|
| 婴儿推车 | ST-20 轻便伞车 | ST-60 高景观 | 登机 / 平躺 / 承重 15 vs 22kg |
| 儿童安全座椅 | CS-04（0–18kg） | CS-12（9–36kg） | 反向安装 / 体重 9–18kg 重叠 |
| 辅食机 | FB-10（600ml） | FB-30（1000ml） | 洗碗机 / 预约 / 保修 12 vs 24 个月 |

**为什么是「3 系列 × 2 型号」而不是 6 个独立商品**：

- 独立商品之间没有可比性，用户问「哪个」时系统不需要区分
- 同系列两个型号参数相近但有关键差异，**逼系统精确回答**
- 6 个 SKU 约 1600 字，落在 1200–1800 目标区间

**品类选母婴而非宠物**：与参考项目（宠物用品）区隔，且与个人项目 baby-ai 呼应。

**参数要求（不是为了字数，是为了区分度）**：

1. 每个 SKU 有 6–8 个可比字段（容量 / 适用体重 / 功率 / 尺寸 / 材质 / 配件）
2. **至少 2 个"相似但不同"的型号**（CS-04 vs CS-12：可反向至 13kg / 仅正向；9–18kg 重叠）
3. 先定 8 道商品题，再按题倒推字段——**写完自然落在 1200–1800 字，不凑字数**

**没有参数交叉，商品题就没有区分度**：型号差异太大时，怎么问都不会混。

## 五、业务库：4 张表

| 表 | 条数 | 必须覆盖的状态 |
|---|---|---|
| `orders` | 15–20 | 待付款 / 待发货 / 已发货 / 已签收 / 退款中 / 已关闭 |
| `logistics` | 15–20 | 正常运输 / 停滞超 3 天 / 已签收未收到 / 异常件 |
| `stock` | 5 | 有货 / 无货 / 预售 / 规格组合无效 |
| `coupons` | 5 | 已过期 / 未达门槛 / 不可叠加 / 已使用 |

**关键不是数量，是状态覆盖。** 没有"已发货不能取消"这类状态，评测就没有素材。

## 六、规则表：3 组

| 规则组 | 判定输入 | 判定输出 |
|---|---|---|
| **退款资格** | 签收日、商品完好、是否定作/鲜活/拆封数字商品 | 可退 / 不可退 / 需人工 |
| **价保** | 下单日、是否降过价、是否参与活动、是否已退 | 补差金额 / 不符合 |
| **订单变更** | 订单状态、承运商、是否已发货 | 可改 / 不可改 / 需人工 |

**规则必须以代码实现，模型只能解释，不能计算。**

## 七、数据来源与合规

| 数据 | 来源 | 合规处理 |
|---|---|---|
| 政策条文 | 真实法规 | 注明条号与出处 |
| 平台细则 | 自造（虚构品牌） | 不与真实平台雷同 |
| 商品参数 | 自造品牌 + 参考真实参数结构 | 不抄商品文案 |
| 订单/物流 | 合成 | 不使用任何真实个人信息 |
| 问法表达 | 参考公开客服数据集（JDDC / Nexdata 等） | **只提炼问法，不复制内容** |

**禁止事项**：
- 不爬取平台数据
- 不使用真实用户信息
- 不整段复制受版权保护的文案

## 八、切分与清洗

### 法规文本（按条切）

```
一级：第 X 条 → 一个 chunk
二级：超过 600 字的条，按（一）（二）再拆，每条保留条头路径
```

**chunk 元数据字段**：

```json
{
  "id": "art-006",
  "chapter": "第二章",
  "article_no": 6,
  "title": "不适用七日无理由退货的商品",
  "text": "（原文）",
  "plain": "（白话摘要，用于检索）",
  "version": "2020修订",
  "source": "https://www.gov.cn/..."
}
```

### 清洗六步

| # | 步骤 | 原因 |
|---|---|---|
| 1 | 去网页导航/页脚/水印 | gov.cn 页面有大量非正文 |
| 2 | 统一全角半角、用简体 | 影响分词与 BM25 |
| 3 | 规范条号（"第 六 条" → "第六条"） | 空格会让条号匹配失效 |
| 4 | 提取章/条/项为独立字段 | 作为 section path |
| 5 | 去掉旧版本，只留 2020 修订版 | 两版并存互相干扰 |
| 6 | 补元数据（版本/机关/日期/URL） | 引用溯源 |

### 两个难点与对策

| 难点 | 表现 | 对策 |
|---|---|---|
| **交叉引用** | 第七条引用《消保法》第二十五条，单条不自足 | 每条加"上下文前缀"（低成本） |
| **条件限定词** | "经消费者确认""查验性开箱不影响完好"易被丢掉 | 切分时不把"但/除…外"切到另一块；并专门出题测 |

### 可选优化：白话摘要（先测再加）

法律原文 embedding 效果差（用词书面），可选做法是每个 chunk 加一行 `plain`：

- 检索向量用 `plain`
- BM25 与生成依据用 `text`

**但这不是必需的。** 语料只有 30–50 个 chunk 时，检索本身很难失败，收益有限。

**触发条件（满足任一再加）**：

| 条件 | 判定 |
|---|---|
| 法规类问题 hit@3 < 0.8 | 加 |
| 语料扩到 100+ chunk | 加 |
| "第六条 vs 第七条"答错率 > 10% | 加，并给每 chunk 补 title |

**判定流程**：不加 plain 先跑一轮 → 看法规类 hit@3 → 低于阈值才加。

**可讲的点**："我没有预先优化，是先测了 recall 再决定加不加。"

---

### 可选：检索侧三段式（来自参考实现）

| 步骤 | 做法 | 什么时候上 |
|---|---|---|
| Query 扩写 | 原始 + 2 条变体，分别检索 | hit@3 < 0.8 时 |
| 多 query 去重 | 按 chunk id 合并，保留最高分 | 同上 |
| head/tail 排列 | 高分证据放头尾，防中间被忽略 | 证据条数 > 6 时 |

**语料 30–50 chunk 时先不做**，先测再决定——与"白话摘要"同一个判断逻辑。

## 十、企业实践对照

> 企业级 RAG 的差距不在模型，在**知识治理**和**结构化优先**。

### 五层知识架构

| 层 | 内容 | 用什么回答 | 本项目 |
|---|---|---|---|
| **实时层** | 订单、库存、账户、物流 | API / SQL，**不走向量** | ✅ 业务库 + 工具 |
| **规则层** | 政策、制度、SOP、法规 | 向量检索（原文 + 白话摘要） | ✅ 5 条法规 + 平台细则 |
| **说明层** | 产品手册、帮助文档、FAQ | 向量检索 | ✅ products.md |
| **历史层** | 历史工单、优质问答 | few-shot 示例 | ⬜ 暂不做 |
| **元数据层** | 版本、生效日期、租户、密级 | 过滤条件，不是检索内容 | ⚠️ 只做版本与生效日期 |

### 企业做法 vs 本项目

| 企业做法 | 企业怎么做 | 本项目怎么做 | 降级理由 |
|---|---|---|---|
| 结构化优先 | 能查库的绝不进检索 | 订单/物流/库存强制走工具路由 | 同左，成本为零 |
| 文档治理 | 版本/负责人/状态/变更影响 | frontmatter + 改版跑评测 | 单人项目，去掉审批流 |
| 元数据过滤 | 租户 + 产品线 + 生效时间 | 只保留 `version` / `effective_from` | 单租户，不需要隔离 |
| 分层评测 | 检索层 / 生成层 / 端到端 / 业务 | 7 桶分能力 + 分桶指标 | 同左 |
| 答案治理 | 引用强制、高风险拒答、待审队列 | 三条硬规则 + 低置信转人工 | 去掉审核队列 |
| 可观测 | trace / 成本 / 延迟 / 命中率 | 日志 + token 统计 | 不接 Langfuse |
| 灰度与 A/B | 按流量分组 | 无 | 没有真实流量 |
| 人工审核队列 | 运营团队 + 工作台 | 只做样例页面 | 无运营 |

### 立刻可借鉴的三条（成本极低）

**① 结构化优先**——写进代码的硬规则

```python
if intent in ("订单查询", "物流查询", "库存价格"):
    return tool_route(...)      # 绝不进向量检索
```

面试可讲："能查库的问题不走向量检索，避免把数据类问题当成知识问答。"

**② 文档 frontmatter**——让知识库像资产，不像一堆笔记

```yaml
---
version: 2026.10
updated: 2026-10-27
effective_from: 2026-10-01
source: https://www.gov.cn/...
owner: me
---
```

改版时 diff 一下，立刻知道哪些评测题可能失效。

**③ 答案侧三条硬规则**——纯规则，不花成本

```
1. 没有证据不出答案（引用强制）
2. 金额 / 时效必须来自工具或规则，模型只能复述
3. 法律 / 医疗建议类直接拒答
```

**这三条是企业最在意、个人项目最容易缺的部分。**

## 十一、决策记录

| # | 决策 | 理由 | 备选（未采用） |
|---|---|---|---|
| 1 | 知识库只做 6 篇 | 4 类意图才需要 KB，再多是维护负担 | 50 篇 FAQ 平铺（边界少、评测价值低） |
| 2 | 法规只取 5 条 | 只有这 5 条产生边界判断 | 全文 30 条（噪声多、切分成本高） |
| 3 | 商品做 **3 系列 × 2 型号（6 个）** | 同系列交叉才有区分度；每个型号都要进评测集 | 12 个独立商品（参考项目做法）/ 20 个 SKU |
| 4 | 业务库每表 5–20 条 | 覆盖状态即可，数量不重要 | 造 1000 条假订单 |
| 5 | 政策用真实法规 | 权威、可引用、边界真实 | 全自造（面试官无从验证） |
| 6 | 商品/订单全合成 | 无版权与隐私风险 | 爬取平台数据（违规） |
| 7 | 法规按"条"切分 | 条是天然语义单元 | 固定长度切分（会切断条件） |
| 8 | 加白话摘要字段 | 提升召回，且可讲优化 | 只用原文（召回差） |
| 9 | 对话数据集只用问法 | 版权与规模问题 | 直接引入整份数据 |
| 10 | 评测按"处理能力"分桶 | 测的是业务正确性 | 按问法风格分桶（只测鲁棒性） |
| 11 | **数据类问题不进向量检索** | 能查库的不检索，避免"检索到相似政策"式的误答 | 全部走 RAG（省事但会错） |
| 12 | **文档加 frontmatter** | 知识库有版本与出处，改版可追溯 | 纯 md 文件（改了什么不知道） |
| 13 | **答案侧三条硬规则** | 引用强制 / 金额走工具 / 高风险拒答 | 只靠 prompt（迟早被绕） |
| 14 | 商品参数以**交叉度**为目标，不追字数 | 型号差异太大会让商品题失去区分度 | 按字数凑到 2500 字（增加噪声） |
| 15 | 白话摘要**先测再加** | 小语料下收益有限，先看 hit@3 再决定 | 一开始就加（过度设计） |
