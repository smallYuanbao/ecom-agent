# 退款评测标注规则（gold set）

> 用途：给 `judge`（模型判定）打分。**`expected` 是人工判断，不是代码输出**——
> 先标后测，否则测的是"代码和它自己一不一致"。
> 关联：`data/eval/refund_gold_20.json`（判定）、`data/eval/refund_10.json`（金额）
> 状态：**待确认**（每个边界都有一个"建议"，需要你拍板）

## 一、`expected` 是三态

| 标签 | 含义 |
|---|---|
| `可退`（`eligible: true`） | 系统应当给出"可退"结论并算金额 |
| `不可退`（`eligible: false`） | 系统应当给出"不能退"结论并说明原因 |
| **`应转人工`**（`needs_human: true`） | 信息不足或规则冲突，系统应当承认判不了 |

**"应转人工"是合法答案，不是"测不出来"。** 一个把"拿不准"硬判成结论的系统，
在这个标签上会稳定失分。

> **不要把它和"功能没做"混在一起**：如果是"补一段数据或规则就能判"，
> 那属于产品缺口（先补规则），不是"系统判不了"。本批 20 条里属于后者的只有
> 「日期倒挂」和「完好程度模糊」两条。

## 二、边界判定（**待你确认**）

每条给"建议 + 依据"。不同意就改，改完这张表就是标注的唯一标准。

### 时间

| # | 情形 | 建议 | 依据 |
|---|---|---|---|
| T1 | 签收**第 7 天**当天申请 | **可退** | 法规：自签收次日起 7 日内 |
| T2 | 第 8 天、原因=无理由 | **不可退**（`out_of_window`） | 同上，超期 |
| T3 | 第 8 天、原因=质量问题 | **可退** | 质量问题不受 7 天限制 |
| T4 | 未签收（`signed_at` 为空）、原因=无理由 | **可退**（`reject_then_refund`，全额） | 平台政策：拒收后全额退（`returns.md`「已发货但未收到时申请退款」） |
| T5 | `signed_at` 早于 `shipped_at`（数据矛盾） | **应转人工** | 日期倒挂，规则无法适用 |

### 商品类别

| # | 情形 | 建议 | 依据 |
|---|---|---|---|
| C1 | 定作款（刻字 / 定制铭牌） | **不可退**（`not_applicable`） | 法规第六条 |
| C2 | 已拆封的奶瓶 / 奶嘴 | **不可退** | 第七条 + 下单页确认 |
| C3 | **未拆封**的奶瓶 | **可退** | 规则只管"拆封后" |
| C4 | 普通商品（推车 / 安全座椅 / 辅食机） | 按时间与完好判 | — |

> **C2/C3 暴露一个数据缺口**：要区分"已拆封 / 未拆封"，`extract` 必须抽出
> `packaging_opened: bool`。当前 schema 里没有这个字段，需要补（见 §五）。

### 完好程度

| # | 用户描述 | 建议 | 依据 |
|---|---|---|---|
| K1 | "拆开快递盒看了一下" | **完好** | 快递外包装属收货必需动作 |
| K2 | "纸箱撕了但商品没动" | **完好** | 同上 |
| K3 | "试穿了一下，吊牌还在" | **完好** | 试穿属查验 |
| K4 | "剪了吊牌" | **不完好**（`not_intact`） | 平台政策 |
| K5 | "穿出门一次" | **不完好** | 超出查验需要 |
| K6 | "辅食机用过一次，洗过了" | **不完好** | 残留食物残渣 |
| K7 | "用了一下，不太确定算不算用过" | **应转人工** | 语义模糊，模型应承认拿不准 |

### 订单状态

| # | 状态 | 建议 | 依据 |
|---|---|---|---|
| S1 | 待付款 | **不可退**（`wrong_status`） | 未支付，无需退款 |
| S2 | 待发货 | **可退**（全额） | 未发货可取消 |
| S3 | 已发货、未签收 | **应转人工** | 需拒收或签收后再申请 |
| S4 | 已签收 | 按时间与完好判 | — |
| S5 | 退款中 | **不可退**（`wrong_status`） | 不可重复申请 |
| S6 | 已关闭 | **不可退**（`wrong_status`） | 订单已关闭 |

## 三、`reason_code` 封闭集合

`judge` 输出与 `expected` 都用这七个值：

| 值 | 含义 |
|---|---|
| `ok` | 可退 |
| `out_of_window` | 超过 7 天 |
| `not_applicable` | 法定/平台不适用类商品 |
| `not_intact` | 商品不完好 |
| `wrong_status` | 订单状态不允许 |
| `reject_then_refund` | 未签收，需拒收后退款 |
| `needs_human` | 应转人工 |

## 四、20 单的构造清单（`expected` 留空待填）

| 组 | 条数 | 覆盖 | 构造要点 |
|---|---|---|---|
| 正常可退 | 4 | T1、普通商品 | 签收 3–6 天、完好、无理由 / 质量问题各半 |
| 超期 | 3 | T2 / T3 | 第 8 天无理由（不可退）、第 8 天质量问题（可退）、第 15 天质量问题（可退） |

## 五、一个必须先补的字段

`judge` 要区分"已拆封 / 未拆封"的奶瓶，但当前 `extract` 只抽三个字段：

```python
{reason_code, item_count, condition_ok}
```

**建议增加 `packaging_opened: bool | None`**：

- 用户明确说"拆了 / 没拆" → true / false
- 没提 → `None`，交给 `judge` 结合上下文判断（拿不准就给低 confidence）

否则 C2/C3 两条规则无法执行。

## 六、标注流程

```
① 确认 §二 的边界表（你逐条拍板）
      ↓
② 我生成 20 条候选 JSON，expected 留空
      ↓
③ 你按边界表逐条填 expected
      ↓
④ 隔一天抽查一半，看不一致率
      ↓
⑤ 定稿，之后不再改（改了要重跑评测）
```

**为什么不能我替你填**：填出来的 `expected` 就是我的判断，测的是"模型和我想得一样吗"，
不是"模型判得对吗"。而且面试被问"这单为什么不能退"，你要能自己答。

## 七、统计口径

评测报告要分开报这三个数，不能只报总准确率：

```
准确率 = 判对 / 总数

错放率 = (gold=不可退 但判可退) / (gold=不可退 的总数)
错拦率 = (gold=可退 但判不可退) / (gold=可退 的总数)
该转却给结论 = (gold=应转人工 但给了可退/不可退) 的条数
```

**两个错误方向代价不同**：错放要多退钱，错拦招客诉。合并成一个数会掩盖问题。
