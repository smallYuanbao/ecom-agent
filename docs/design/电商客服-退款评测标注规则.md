# 退款评测标注规则（gold set）

> 用途：给 `judge`（模型判定）打分。**`expected` 是人工判断，不是代码输出**——
> 先标后测，否则测的是"代码和它自己一不一致"。
> 关联：`data/eval/refund_gold_20.json`（判定）、`data/eval/refund_10.json`（金额）
> 状态：**待确认**（每个边界都有一个"建议"，需要你拍板）

## 一、`expected` 是三态

| 标签 | 含义 |
|---|---|
| `可退`（`eligible: true`） | 系统应当给出"可退"结论并算金额 |
| `不可退`（`eligible: false`） | 系统应当给出"不能退"结论并说明原因 |
| **`应转人工`**（`needs_human: true`） | 信息不足或规则冲突，系统应当承认判不了 |

**"应转人工"是合法答案，不是"测不出来"。** 一个把"拿不准"硬判成结论的系统，
在这个标签上会稳定失分。

> **不要把它和"功能没做"混在一起**：如果是"补一段数据或规则就能判"，
> 那属于产品缺口（先补规则），不是"系统判不了"。本批 20 条里属于后者的只有
> 「日期倒挂」和「完好程度模糊」两条。

## 二、边界判定（**待你确认**）

每条给"建议 + 依据"。不同意就改，改完这张表就是标注的唯一标准。

### 时间

| # | 情形 | 建议 | 依据 |
|---|---|---|---|
| T1 | 签收**第 7 天**当天申请 | **可退** | 法规：自签收次日起 7 日内 |
| T2 | 第 8 天、原因=无理由 | **不可退**（`out_of_window`） | 同上，超期 |
| T3 | 第 8 天、原因=质量问题 | **可退** | 质量问题不受 7 天限制 |
| T4 | 未签收（`signed_at` 为空）、原因=无理由 | **可退**（`reject_then_refund`，全额） | 平台政策：拒收后全额退（`returns.md`「已发货但未收到时申请退款」） |
| T5 | `signed_at` 早于 `shipped_at`（数据矛盾） | **转人工**——但属**守卫测试**，不进 gold set | 日期倒挂（补录 / 时区 / ERP 回传），见下 |

> **T5 为什么不在 gold set 里**：它在 `validate` 阶段就被拦下，**到不了 `judge`**。
> 放进 gold set 只会白送一分、稀释准确率。它该由守卫单测覆盖
> （`tests/test_rules_validate.py`），并要求同时落 `trace_span` 与低置信池
> （`source=data_anomaly`）——否则只能发现"又倒挂了"，查不到上游是谁的锅。
>
> **注意它和 T4 的区别**：`NULL` 是"还没有"（正常业务状态），倒挂是"有但错了"（数据故障）。

### 商品类别

| # | 情形 | 建议 | 依据 |
|---|---|---|---|
| C1 | 定作款（刻字 / 定制铭牌） | **不可退**（`not_applicable`） | 法规第六条 |
| C2 | 已拆封的奶瓶 / 奶嘴 | **不可退** | 第七条 + 下单页确认 |
| C3 | **未拆封**的奶瓶 | **可退** | 规则只管"拆封后" |
| C4 | 普通商品（推车 / 安全座椅 / 辅食机） | 按时间与完好判 | — |

> **C2/C3 暴露一个数据缺口**：要区分"已拆封 / 未拆封"，`extract` 必须抽出
> `packaging_opened: bool`。当前 schema 里没有这个字段，需要补（见 §五）。

### 完好程度

| # | 用户描述 | 建议 | 依据 |
|---|---|---|---|
| K1 | "拆开快递盒看了一下" | **完好** | 快递外包装属收货必需动作 |
| K2 | "纸箱撕了但商品没动" | **完好** | 同上 |
| K3 | "试穿了一下，吊牌还在" | **完好** | 试穿属查验 |
| K4 | "剪了吊牌" | **不完好**（`not_intact`） | 平台政策 |
| K5 | "穿出门一次" | **不完好** | 超出查验需要 |
| K6 | "辅食机用过一次，洗过了" | **不完好** | 残留食物残渣 |
| K7 | "用了一下，不太确定算不算用过" | **应转人工** | 语义模糊，模型应承认拿不准 |

### 订单状态

| # | 状态 | 建议 | 依据 |
|---|---|---|---|
| S1 | 待付款 | **不可退**（`wrong_status`） | 未支付，无需退款 |
| S2 | 待发货 | **可退**（全额） | 未发货可取消 |
| S3 | 已发货、未签收 | **应转人工** | 需拒收或签收后再申请 |
| S4 | 已签收 | 按时间与完好判 | — |
| S5 | 退款中 | **不可退**（`wrong_status`） | 不可重复申请 |
| S6 | 已关闭 | **不可退**（`wrong_status`） | 订单已关闭 |

## 三、`reason_code` 封闭集合

`judge` 输出与 `expected` 都用这七个值：

| 值 | 含义 |
|---|---|
| `ok` | 可退 |
| `out_of_window` | 超过 7 天 |
| `not_applicable` | 法定/平台不适用类商品 |
| `not_intact` | 商品不完好 |
| `wrong_status` | 订单状态不允许 |
| `reject_then_refund` | 未签收，需拒收后退款 |
| `needs_human` | 应转人工 |

## 四、gold set 的入选原则

> **只收"能到达 `judge` 节点"的案例。**

流水线里排在 `judge` 之前的检查会拦下若干情形，这些到不了模型，测不到判定能力：

| 被谁拦下 | 案例类型 | 该在哪测 |
|---|---|---|
| `intake` / `need_info` | 缺订单号 | 状态机转移测试 |
| `validate` | 越权（不是本人的单） | 仓库层 + validate 测试 |
| `validate` | 日期倒挂（T5） | validate 守卫测试 |
| `query_data` | 政策检索为空 | 子图测试 |

**它们的正确性同样重要，只是不能用 judge 的准确率来衡量。**

## 五、20 单的构造清单（`expected` 留空待填）

| 组 | 条数 | 覆盖 | 构造要点 |

| 超期 | 3 | T2 / T3 | 第 8 天无理由（不可退）、第 8 天质量问题（可退）、第 15 天质量问题（可退） |

## 六、一个必须先补的字段

`judge` 要区分"已拆封 / 未拆封"的奶瓶，但当前 `extract` 只抽三个字段：

```python
{reason_code, item_count, condition_ok}
```

**建议增加 `packaging_opened: bool | None`**：

- 用户明确说"拆了 / 没拆" → true / false
- 没提 → `None`，交给 `judge` 结合上下文判断（拿不准就给低 confidence）

否则 C2/C3 两条规则无法执行。

## 七、标注流程

```
① 确认 §二 的边界表（你逐条拍板）
      ↓
② 我生成 20 条候选 JSON，expected 留空
      ↓
③ 你按边界表逐条填 expected
      ↓
④ 隔一天抽查一半，看不一致率
      ↓
⑤ 定稿，之后不再改（改了要重跑评测）
```

**为什么不能我替你填**：填出来的 `expected` 就是我的判断，测的是"模型和我想得一样吗"，
不是"模型判得对吗"。而且面试被问"这单为什么不能退"，你要能自己答。

## 八、统计口径

评测报告要分开报这三个数，不能只报总准确率：

```
准确率 = 判对 / 总数

错放率 = (gold=不可退 但判可退) / (gold=不可退 的总数)
错拦率 = (gold=可退 但判不可退) / (gold=可退 的总数)
该转却给结论 = (gold=应转人工 但给了可退/不可退) 的条数
```

**两个错误方向代价不同**：错放要多退钱，错拦招客诉。合并成一个数会掩盖问题。

## 十、困难组（`refund_gold_hard_10.json`，10 条）

### 为什么还要一组

原有 20 条建成后跑了规则实现，结果 **20/20 全对**。

这意味着：**这批题分不出"模型判定"和"规则判定"**。模型就算 20/20，也只是打平；
错一条就是负优化。但这不代表模型没用，只代表题太简单。

所以另建一组，专门挑**规则判不了、或规则大概率判错**的案例。
这组才是模型的考场。

### 两组分工

| 组 | 文件 | 测什么 | 门槛 |
|---|---|---|---|
| 简单组 | `refund_gold_20.json` | 模型**有没有退化**（规则覆盖范围内不能输） | 准确率 ≥ 90% |
| 困难组 | `refund_gold_hard_10.json` | 模型**有没有增量价值**（规则的空能不能补） | A 组 ≥ 3/4，B 组 ≥ 4/6 |

**规则基线已实测：困难组 2/10（A 组 2/4、B 组 0/6）。**

> ⚠️ **B 组的 0/6 是构造结果，不是抽样估计。**
> 这 6 条是按"怀疑规则判错"挑出来的，规则全错是设计使然。
> 所以它**不能**用来估算规则在线上真实准确率，也**不能**拿"超过 0"当门槛——
> B 组用绝对门槛 4/6，证明模型不是靠赢一个已知错误的基线取胜。

> **分组会随规则演进而变。** H04 原在 B 组；Ch03 Task 10 修完规则 8 后，
> 代码对「质量问题 + condition_ok=false」改为返回 `None`，H04 因此移入 A 组。
> 分组必须描述**当前**的规则行为，否则指标会描述一个已不存在的事实。

**如果模型在困难组也拿不到 7/10，结论就是"该直接用规则"**——
这个结论要在报告里如实写，不能只报一个总数掩盖。

### A 组：规则返回 `None`（4 条）

> `judge_eligibility` 返回 `None` 表示"代码也判不了"，不是"不可退"。

| ID | 情形 | 规则为什么判不了 |
|---|---|---|
| H01 | 「用了一下，不太确定算不算用过」 | `condition_ok` 抽不出来（K7） |
| H02 | 「不想要了，能退吗」 | 用户没描述商品状态，`condition_ok` 为 `None` |
| H03 | 已签收但 `signed_at` 为空 | 7 天窗口没有起算点（数据缺口） |
| H04 | 辅食机异响，试过一次 | 质量问题 + `condition_ok=false`：代码分不清痕迹是缺陷造成的还是用户造成的，不否决 |

**A 组的验收口径**：与人工标注的一致率 ≥ 3/4。

这里刻意**不奖励"给结论"**。A 组的四种标注分别是：

| ID | 标注 | 为什么 |
|---|---|---|
| H01 | `needs_human` | 语义真模糊，承认判不了 |
| H02 | **`ok`** | 7 天内无理由可退是默认成立的，用户没说状态就**说明白**，不是转人工 |
| H03 | `needs_human` | 签收时间缺失，窗口无法核实 |
| H04 | **`ok`** | 异响不开机发现不了，"试了一次"是验证缺陷，不是把商品用旧了 |

> H02 是这组唯一"该给结论"的题：**用户没说 ≠ 系统判不了**。
> 真实客服的回答是"可以退，请保持商品完好寄回"——完好是退货前提，不是申请门槛。
> 若 H02 也标 `needs_human`，A 组三条全与规则一致（规则返回 `None`），这组就失去了区分度。

### B 组：规则判得出，但结论错（6 条）

| ID | 情形 | 规则的结论 | 人工标注 | 可疑在哪 |
|---|---|---|---|---|
| H05 | 客服口头承诺可退，已超 7 天 | `out_of_window` 不可退 | 转人工 | 承诺若成立属平台责任，需人工核实 |
| H06 | 刻字定制推车，已发货未签收 | `reject_then_refund` 可退 | **不可退 `not_applicable`** | 定作商品法定不适用，规则 5 排在类别规则之前 |
| H07 | 「送的奶瓶能退吗」 | `ok` 可退 | 转人工 | 订单快照里**没有赠品字段**，规则与模型都缺数据 |
| H08 | 两件都拆，一件用了、一件没动 | `not_intact` 不可退 | **可退 `ok`** | 退货件本身完好，`condition_ok` 区分不了按件 |
| H09 | 快递放门口淋雨 | `not_intact` 不可退 | 转人工 | 损坏由物流造成，责任归属需人工核实 |
| H10 | 奶瓶只拆外箱、内塑封未动 | `not_applicable` 不可退 | **可退 `ok`** | 第七条管的是"拆封"（内包装），`packaging_opened` 区分不了拆到哪一层 |

**结果：规则 0/6。** 其中 H06 是**规则表顺序缺陷**，其余是**字段粒度不足**或**规则表无覆盖**。

> H06 的标注过程本身说明了一件事：最初被标成 `not_intact`（不完好），
> 但商品**还没收到**，谈不上完好与否——正确理由是 `not_applicable`（法定不适用）。
> 理由码选错，会让答对的模型被判成错。

> **6 条规则全错，模型都有机会拿分**：
> H06 / H08 / H10 应判可退，H05 / H09 应转人工，H07 缺数据也该转人工。
>
> 如果规则表按标注修正了顺序，基线上去了，这组题就要重新挑——
> 这是**好事**：说明规则在进步，模型该去攻新的长尾。H04 已经这样移出过一次。

### 结构守卫

`tests/test_refund_gold_hard.py` 除了格式，还锁住两个性质：

- `test_group_a_is_undecidable_by_rules`：A 组规则必须返回 `None`
- `test_group_b_is_decided_by_rules`：B 组规则必须给出结论

**这两条失败不是"测试该改"，是"案例挑错了"**——
规则哪天能判 A 组了，A 组就不再衡量模型的增量价值。
