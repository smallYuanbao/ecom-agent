## 背景

D12 定的是**单个工具**的超时与重试，M8 定的是**同一会话**的并发。这一维补的是中间和外围：

```
用户点击 ──► 请求进入 ──► 图执行（多节点、多工具） ──► 流式返回 ──► 结束
              ↑                                        ↑
           限流/幂等                              断流怎么办
                        ↑
                  总预算、取消
```

**单点都定好了，端到端还没定。**

---

## C1 · 用户中途离开或点"停止"

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 不处理 | 后台继续跑完，结果丢弃 | 实现最简 | 白烧 token；写操作可能已执行 |
| **B. 取消未完成的调用** | 监听断连，取消进行中的 LLM/工具调用 | 省钱、快速释放资源 | 可能停在半截状态 |
| C. 取消并回滚 | 取消 + 撤销已产生的写操作 | 最干净 | 实现复杂，回滚本身可能失败 |

**推荐：B**

规则：

```
检测到客户端断开
  ├─ 取消进行中的 LLM 流式调用
  ├─ 已落库的用户消息保留（不能删，否则回放断裂）
  ├─ 已完成的节点结果保留在 checkpointer
  └─ 正在进行的写操作（建单/退款）→ 让它跑完，不取消
```

**为什么写操作不取消**：写操作一旦发出，取消只会让你不知道它成没成。**宁可让它完成，靠 `request_id` 幂等**。

### 落地细节（两条硬规则）

**① 无论怎么结束，都要在 `finally` 落库**

参考实现的回答是在 `log_node`（图的**终端节点**）里写库的：

```
… → respond → log → END
                 ↑ 回答在这里才落库
```

**用户中途关页面 → `log` 没跑 → 数据库里只有用户消息，没有回答**，回放时看到的就是「问了一句，系统没答」。

正确做法：

```python
try:
    async for chunk in stream:
        yield chunk
        buffer.append(chunk)
    status = "completed"
except (asyncio.CancelledError, GeneratorExit):
    status = "cancelled"
except Exception:
    status = "error"
finally:
    # 不管怎么结束，都把已生成的部分落库
    save_assistant_message(content="".join(buffer), status=status)
```

**② 消息带 `status` 字段**

`completed` / `cancelled` / `error`——回放时能区分「答完了」「答到一半」「出错了」。

### 取消的分级

| 动作 | 是否取消 |
|---|---|
| LLM 流式调用 | ✅ 取消 |
| 只读工具（查订单/库存） | ✅ 取消 |
| **写操作（建单/退款）** | ❌ **让它跑完**，靠 `request_id` 幂等 |

**反方理由**：取消会留下"半截状态"（图停在某个节点），下次恢复要知道从哪继续。如果不取消，状态总是完整的。

**你的选择**：___B___

## C2 · 流式断流（SSE 断开）

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 不支持 | 断开即丢，用户重新提问 | 最简 | 重复生成，体验差 |
| B. Last-Event-ID 续传 | 服务端缓存事件，按 id 续发 | 标准做法 | 实现复杂，需要事件存储 |
| **C. 重连补历史 + 继续** | 记录已生成片段；重连时先补发，再继续 | 体验接近 B，实现简单 | 需要按 conversation 存片段 |

**推荐：C**

```
生成时：每 N 个 token 追加到 buffer（按 message_id）
断流后：前端带 last_offset 重连
服务端：先补发 buffer[0:offset]，再继续生成
```

**关键**：**不重新生成**——重生成会得到不同措辞，用户会看到内容跳变。

**反方理由**：多一份 buffer 存储和清理逻辑；如果用户很少遇到断流，A 也能接受。

**你的选择**：__C____

## C3 · 限流

| 选项 | 做法 | 说明 |
|---|---|---|
| **A. 单用户每分钟 N 条** | 如 10 条/分钟，超出返回 429 | 防误触和脚本 |
| B. 不限流 | 靠并发锁兜底 | 一个脚本就能把服务打满 |
| C. 全局 QPS 限流 | 按总请求数限 | 单人项目没必要 |

**推荐：A（10 条/分钟）**

- 实现：进程内滑动窗口（单实例足够）
- 超限返回：`429` + 「操作太频繁，请稍后再试」
- **不计入**：静态资源、健康检查

**反方理由**：限流会误伤正常用户（比如反复修改问题）；单人项目可能永远触发不到。但**没有限流，一个循环脚本就能把钱包烧穿**。

**你的选择**：__A____

## C4 · 后台任务与用户请求并发

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 共用会话锁** | 摘要/清理与用户请求抢同一把 `conversation_id` 锁 | 一致性最好 | 摘要会阻塞用户请求 |
| B. 只写不同表 | 约定：摘要只写 summaries，清理只改 active_flow | 互不阻塞 | 需要纪律，容易破 |
| C. 不加控制 | 谁先谁后看运气 | 简单 | 状态可能互相覆盖 |

**推荐：B + A 的混合**

```
摘要任务：只写 conversation_summaries（不碰 messages、不碰 active_flow）→ 不加锁
超时清理：改 active_flow，用乐观锁
   UPDATE conversations SET active_flow=NULL
   WHERE id=? AND updated_at=?          ← 版本不匹配就放弃
```

**理由**：摘要不该阻塞用户请求（它慢），但清理必须防覆盖（它和用户写同一字段）。

**反方理由**：混合策略要记两套规则，容易出错；全用一把锁最简单，但摘要会拖慢请求。

**你的选择**：__B + A 的混合____

## C5 · 端到端总超时

> **2026-10-28 重开**：产品定位改回 C 端消费者，原定的 60s 是按"坐席能等"设计的，需要收紧。

| 选项 | 做法 | 说明 |
|---|---|---|
| **A. 总预算 30s（C 端）** | 15s 给进度提示，30s 降级返回 | 消费者耐心边界 |
| B. 总预算 60s | 坐席场景的值 | C 端等不到这么久 |
| C. 不设总预算 | 各工具各自超时 | 最坏 10 步 × 5s = 50s+，用户干等 |

**推荐：A（30s）**

```
0s      用户发送
15s     还没出结果 → 前端进度提示「还在核算，马上好」
30s     未完成 → 返回已生成部分 + 「处理超时，请稍后再试」
```

**为什么是 30s**：

| 场景 | 可接受等待 |
|---|---|
| 坐席（同时处理多单） | 60s 可接受 |
| **消费者（盯着屏幕）** | **15–30s 是上限** |

**必须实测**：跑 10 次完整退费，看 P95 耗时。

```
P95 < 20s  → 30s 合理
P95 > 30s  → 要么优化链路，要么承认会频繁超时
```

**和 D12 的关系**：单工具 2–5s、ReAct 最多 10 步，理论最坏 50s。**30s 预算意味着必须限制步数或工具数量**——如果实测发现经常撞线，要把 `max_agent_steps` 调小（如 6 步）。

**Ch07 语义证据闸（A 出口）**：只有 top1 相似度落在 `[0.55, 0.60)` 的边界样本，
才多调一次证据自评。它独立设置 **3s 超时、不重试、失败 fail-closed**，
不能沿用分类任务的 30s 超时；C/E 路径不受影响。A 出口目标 p95 ≤ 6s，
边界样本最坏额外 3s；总预算仍是 30s。

**反方理由**：30s 对多步退费可能不够，会导致"其实能算完但被掐断"；60s 更安全，但消费者等不了。

**你的选择：A（30s）** —— 15s 进度提示、30s 降级返回；上线前实测 P95，必要时下调步数。

## C6 · 客户端重发（网络抖动）

| 选项 | 做法 | 说明 |
|---|---|---|
| **A. client_message_id 幂等** | 前端生成 id，服务端按 id 去重 | 重复请求只执行一次 |
| B. 不做 | 重发就重跑 | 可能建两张单 |
| C. 服务端按内容哈希去重 | 相同内容 60s 内只处理一次 | 用户真问两遍会被吞 |

**推荐：A**

```sql
UNIQUE (conversation_id, client_message_id)
```

**为什么不用内容哈希**：用户可能真的连问两次同一句话（"再说一遍"），按内容去重会吞掉第二次。

**反方理由**：前端要多生成一个 id，服务端要多一个唯一索引；但如果没做，网络一抖就可能重复建单。

**你的选择**：__A____

## 本维需要新增的东西

| 类型 | 内容 | 对应决策 |
|---|---|---|
| 请求处理 | 断连监听 + 取消未完成调用 | C1 |
| 存储 | 流式片段 buffer（按 message_id） | C2 |
| 中间件 | 单用户滑动窗口限流 | C3 |
| 任务 | 摘要不加锁 / 清理用乐观锁 | C4 |
| 请求处理 | 总预算 deadline 传递 | C5 |
| 表字段 | `client_message_id` + 唯一索引 | C6 |

### 三个必测场景

1. **断流重连**：生成到一半杀连接 → 重连 → 不重复、不跳变
2. **连点发送**：同一秒发两条 → 第二条被限流或排队（M8），不出现两套状态
3. **总超时**：模拟工具慢 20s → 60s 时降级返回部分结果，不无限等待
