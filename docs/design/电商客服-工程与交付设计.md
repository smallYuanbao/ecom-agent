## L0 · 产品定位（先定这个，其余都受它影响）

**本项目：C 端消费者自助客服。**

| 项 | 内容 |
|---|---|
| 用户 | **消费者（C 端）** |
| AI 角色 | 直接与消费者对话，处理咨询与售后 |
| 界面 | 聊天窗 + 轻量进度提示 |
| 流程深度 | C 出口 8 状态等深度设计**保留**（消费者也受益于准确的金额与判断） |
| **B 端坐席台** | **不在本项目范围**，作为后续配套（同一套后端，换前端与话术归属） |

**为什么先定这个**：它决定界面形态（L4）、话术给谁、README 怎么定位、演示怎么讲。

**为什么 C 端也能承载深流程**：消费者不关心里面有几个状态，但会感受到"它很快算出了准确的金额，并且说清了依据"。

## L1 · 评测怎么跑

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 接 EvalFlow** | 系统暴露 `/api/chat` + `/api/meta`，用已有平台跑 | 复用成熟平台；**这是你的差异化** | 要按平台契约实现接口 |
| B. 自己写脚本 | 一个 `eval.py` 跑完打印指标 | 灵活、快 | 重复造轮子，且没有可比性管理 |
| C. 不评测 | 手工试几条 | 零成本 | 面试问"你怎么证明有效"时答不出 |

**推荐：A**

**关键**：选 A 会**反向决定 API 契约**——必须暴露：

```
POST /api/chat          {conversation_id, message} → 流式
GET  /api/meta          → {version, model, kb_version, prompt_version}
```

`/api/meta` 是 EvalFlow 做快照必需的（K6 的 `kb_version` 就来自它）。

**反方理由**：接平台要处理流式、超时、并发，比写脚本麻烦；但**你已经把平台做好了，不用白不用**。

**你的选择**：___A___

## L2 · 多久跑一次评测

| 选项 | 做法 | 说明 |
|---|---|---|
| **A. 手动，改了就跑** | 改 prompt / 规则 / 知识库后跑一轮 | 40 条几分钟，够用 |
| B. CI 自动跑 | push 触发 GitHub Actions | 有仓库后可选 |
| C. 定时跑 | 每天一次 | 没有线上流量，跑了个寂寞 |

**推荐：A**

**规则**：

```
改了以下任一项 → 必须跑：
  · 系统 prompt / 判定规则
  · 知识库内容（kb_version 变了）
  · 工具契约
```

**反方理由**：手动容易忘；但 CI 对一个还没上线的项目是过度工程。

**你的选择**：__A____

## L3 · gold（标准答案）从哪来

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 客观项人工手算，主观项 AI 预标** | 金额/资格手算；话术质量 AI 打分 + 抽检 | 客观项可靠，成本可控 | 主观项有偏差 |
| B. 全部人工 | 最可靠 | 40 条 × 5 维度，工作量大 |
| C. 全部 AI 预标 | 快 | **客观项也会错，评测就失去意义** |

**推荐：A**

| 指标 | gold 来源 |
|---|---|
| **金额、是否该转人工、触发的红线** | **必须手算**（客观，可复核） |
| 话术质量、覆盖度 | AI 预标 + 你抽检 5 条 |

**为什么客观项必须手算**：金额算错是"事实错误"，AI 预标也可能错，而且错了你无法察觉。

**这条你在 EvalFlow 里已经踩过**——AI 预标 gold 后 `context_precision` 偏差 −0.35，说明预标不可全信。

**你的选择**：___A___

## L4 · 前端做到什么程度

> **定位前提见 L0：C 端消费者自助。** 三栏工作台属于 B 端方向，列为后续。

| 选项 | 范围 | 工作量 |
|---|---|---|
| A. 只做聊天窗 | 对话 + 流式 | 2–3 天 |
| **B. 聊天 + 轻量进度** | 右侧显示「正在核对订单 / 已算出金额 / 等待确认」，不暴露内部细节 | 3–4 天 |
| C. 三栏工作台 | 流程高亮 + 证据编号 + 金额明细 + 审核页 | 8–10 天（**B 端，后续**） |

**推荐：B**

```
┌─────────────┬──────────────┐
│             │ 正在核对订单  │
│   对话区     │ ✓ 已查到订单  │
│             │ ✓ 已算出金额  │
│             │ ○ 等待您确认  │
└─────────────┴──────────────┘
```

**原则：给进度，不给内部细节。**

| 可以展示 | 不要展示 |
|---|---|
| 到哪一步了 | 命中了第几条法规 |
| 算出多少钱 | 规则 id、置信度分数 |
| 需要用户做什么 | 工具调用链 |

**为什么选 B**：退费流程有 8 个状态，用户等了十几秒会怀疑"是不是卡住了"；进度提示解决的是**等待焦虑**，不是炫技。

**为什么不做 C（工作台）**：那是给坐席看的，消费者看"依据第六条"没有意义。**作为 B 端配套留到后续。**

**反方理由**：进度提示需要后端把状态透传给前端，多一层接口；纯聊天窗（A）最省事，但用户等待时没有反馈。

**你的选择**：__B____

## L5 · 怎么起服务

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 本地 venv + SQLite** | `uv sync` + `uvicorn` | 最快，调试方便 | 别人要装 Python |
| B. docker compose | app + db + redis 一键起 | 环境一致 | 调试慢，镜像大 |
| C. 云部署 | 有公网地址 | 演示方便 | 成本和维护 |

**推荐：A 为主，B 进 README**

```
快速开始（本地）：
  uv sync && uv run uvicorn app.main:app --reload

可选（Docker）：
  docker compose up
```

**理由**：你自己开发用 A；但 README 里给 B，面试官想看"工程化"时能加分。

**反方理由**：没有 Docker 会显得不够"工程"；但**一个能 30 秒跑起来的项目比一个需要装 Docker 的项目更容易被体验**。

## L7 · 日志与可观测

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 只做结构化日志 | JSON + trace_id | 零依赖 | 调用链要自己拼 |
| B. 直接接 Langfuse | 依赖外部服务 | 调用树好看 | 平时排障反而慢；部署重 |
| **C. 分层接入** | 日志为主 + Langfuse 可选 + trace 表按 span 模型 | 三者互补，零硬依赖 | 多一层抽象 |

**推荐：C**

### 三层各管什么

| 层 | 作用 | 何时用 |
|---|---|---|
| **结构化日志** | 日常排障：按 `trace_id` 看这一次请求走了什么 | 写代码时 |
| **trace 表（span 模型）** | 数据源：回放、评测、统计 | 跑评测 / 复盘 |
| **Langfuse** | 展示：调用树、成本聚合 | 演示 / 深度排查 |

**三者不重复**：日志是"看"，trace 表是"存"，Langfuse 是"给别处看"。

### Langfuse 做成可选开关（借鉴参考实现）

```
LANGFUSE_PUBLIC_KEY=...
LANGFUSE_SECRET_KEY=...
LANGFUSE_BASE_URL=http://localhost:3000    ← 支持自部署，数据不出门
```

**四个要点**：

| # | 做法 | 原因 |
|---|---|---|
| 1 | **三变量缺一即 no-op** | 没配置时完全不启用 |
| 2 | **未配置时不 import langfuse** | 没装依赖也能跑 |
| 3 | **CallbackHandler 挂图编译时** | 节点零侵入 |
| 4 | **base_url 指向自部署** | 数据不出门 |

参考实现的注释原话：「观测是增强，不是依赖」。

### trace 表按 span 模型设计

```sql
trace_span (
  trace_id,        -- 一次请求
  span_id,         -- 一个节点/工具调用
  parent_span_id,  -- 支持树形
  name,            -- node:compute / tool:query_order
  start_at, end_at,
  attrs JSON       -- tokens / 结果摘要 / 错误
)
```

**理由**：这个结构和 Langfuse / OpenTelemetry 的 span 模型一致。**将来接任何 APM，加一个 exporter 即可，业务代码不用改。**

**反着做（只写文本日志）的代价**：将来要接可观测平台，得把所有埋点重做一遍。

**日志样例**：

```json
{"ts":"...","trace_id":"abc","conv":12,"node":"compute",
 "event":"refund_calculated","amount":299,"rules":["R2","R5"]}
```

**trace_id 必须贯穿**：入口生成 → 节点日志 → 工具调用 → trace 表。

**反方理由**：三层要维护两份记录（日志 + trace 表）；如果只是 demo，A 一层就够。但 trace 表同时是**评测与回放的数据源**，不是纯观测设施。

**你的选择**：__C____

## L8 · 文档与演示

| 项 | 内容 |
|---|---|
| **README** | 五段式：定位 / 架构图 / 快速开始 / 设计取舍 / 评测结果 + 局限 |
| **演示脚本** | 四个场景：正常退费 / 边界转人工 / 知识问答 / **中途离开再回来** |
| **截图** | 主界面 + 状态面板 + 评测报告 |
| **视频** | 2 分钟，从提问到出结果 |

**README 五段式（不要写成长文）**：

```markdown
# 电商客服 Agent
一句话：把退费核算从人工 30 分钟压到 2 分钟，且金额可审计。

## 架构
[一张图：主图 5 出口 + C 出口 8 状态]

## 快速开始
uv sync && uv run uvicorn ...

## 设计取舍
- 金额由代码算，模型只复述（为什么）
- 追问用独立状态而非 interrupt（为什么）
- 守卫失败按不通过处理（为什么）

## 评测
40 条评测集，金额准确率 X%，转人工判定 Y%
局限：无真实用户，数据为合成
```

**"局限"这一节必须写**——它是最能体现诚实和专业度的地方。

### 四个演示场景

| # | 场景 | 验证什么 |
|---|---|---|
| 1 | 正常退费：「推车用了两次能退吗」→ 算金额 → 确认 | 主链路 |
| 2 | 边界转人工：「超过 7 天了」→ 说明原因 → 转人工入口 | 守卫与话术 |
| 3 | 知识问答：「退货政策是什么」→ 引用第六条 | 检索与引用 |
| 4 | **中途离开再回来**：退费问到一半 → 问别的 → 回到退费 | **park + 恢复（M5/M6）** |

**第 4 个是 C 端最真实的场景**，也是多轮设计最容易被忽略的验证点。

### 三个子决策

| # | 决策 | 选项 | 建议 |
|---|---|---|---|
| **L8-a** | 视频做不做 | 做 / 不做 | **做**，但等前端与评测定稿后（约 2 小时） |
| **L8-b** | 仓库公开吗 | 公开 / 私有 | **公开**（前提：无课程代码、无真实数据、`.env` 已 gitignore） |

**仓库公开是本项目与参考项目最大的区别**：那个不能公开，这个可以——这也是"归属干净"的最直接证明。

**你的选择：按 L8-a/b/c 执行** —— 视频做（面试前）、仓库公开、README 五段式 ≤150 行。
