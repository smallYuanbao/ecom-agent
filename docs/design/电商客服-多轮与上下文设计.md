## 背景：为什么单独拆一维

其余四篇覆盖了"单轮怎么处理"，但退费场景天然跨轮：

```
用户：我要退费
系统：请提供订单号
用户：1001          ← 这一句怎么接回流程？
系统：核对到订单…
用户：等等，你们几点上班？   ← 中途改话题怎么办？
```

**这三步任何一步处理不好，用户就要重来。**

## M1 · 消息存哪、存多少

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 只存内存 | 进程内列表，重启即丢 | 实现最简 | 重启后会话消失，无法审计 |
| **B. DB 存全量 + 窗口裁剪** | `messages` 表存所有消息，送模型时只取窗口 | 可回放、可审计；成本可控 | 需要窗口逻辑 |
| C. 只存最近 N 轮 | 表里只留最近 N 轮 | 表小 | 无法审计，历史问题查不到 |

**推荐：B**

理由：**存全量是为了回放和审计，送窗口是为了成本和延迟**——两件事分开。

**反方理由**：表会一直长，需要归档策略；如果只做 demo，A 也够用。

**你的选择**：___B___

### 表结构

```sql
CREATE TABLE messages (
  id              INTEGER PRIMARY KEY,
  conversation_id INTEGER NOT NULL,
  role            TEXT NOT NULL,      -- user / assistant / tool
  content         TEXT,
  tool_calls      JSON,               -- assistant 发起的工具调用
  tool_call_id    TEXT,               -- tool 消息对应的调用 id
  status          TEXT,               -- completed / cancelled / error（助手消息用）
  meta            JSON,               -- intent / route / citations（可选）
  created_at      DATETIME
);
CREATE INDEX idx_conv_created ON messages(conversation_id, created_at);
```

### 锚点约定（重要）

**每轮取出历史消息时，把 DB 的 `id` 带回消息对象**（如 `HumanMessage(id=f"db-{msg_id}")`）。

**为什么**：
- 摘要边界、滑窗边界都要用消息 id 表示，才能与 DB 对齐
- 回放时能精确还原"当时看到的是哪几条"
- 后续升级成三层渲染时，锚点机制不用改

**没有锚点的后果**：边界只能按"第几条"记，一旦有消息补录/删除，边界就错位。

## M2 · 窗口与摘要

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 只滑窗 | 保留最近 N 轮 | 简单 | 早期关键信息（订单号）丢失 |
| **B. 滑窗 + 滚动摘要** | 最近若干轮原文 + 更早的压成摘要 | 长对话不丢关键事实 | 需要摘要任务与触发条件 |
| C. 全量塞进去 | 所有历史都进 prompt | 不丢信息 | token 爆掉，成本线性增长 |

**推荐：B**

### 预算按块分配（不要只设一个全局阈值）

```
窗口总量
 ├─ 系统提示 + 工具 schema      （固定开销）
 ├─ 检索证据                    （按 top_k 与 chunk 长度估算）
 ├─ 注入的摘要段                （最近若干段）
 ├─ 输出预留                    （max_tokens）
 └─ 剩下的 → 滑窗预算
```

**触发条件**：滑窗实际占用超过**滑窗预算**时压缩，不是"全局 70%"。

**为什么**：后面如果加大证据条数或加长系统提示，全局 70% 会悄悄把滑窗挤没，而你不会收到任何报错。

### 三层渲染（可先做两层，留好扩展）

| 层 | 内容 | 处理 |
|---|---|---|
| 层 1 | 最近 N 轮 | 原文 |
| 层 2 | 稍早的历史 | **半压**：工具结果压成一行，用户/助手消息保留 |
| 摘要 | 更早的 | 滚动摘要段落 |

**先做"层 1 + 摘要"两层即可**，但消息要带 id 锚点（见 M1），以后加层 2 不用改表。

### 工具结果压缩

工具返回往往比对话长得多（一个订单 JSON 可能几百字）。

**规则**：工具结果超过 N 字符（建议 200）就压成一行摘要再进历史，原始结果进 trace。

**否则**：一次 ReAct 走 5 步，光工具结果就能把窗口吃光。

### 边界一次挪到位

压缩后重算新边界时，**一次挪到位，不要每轮微调**。

**原因**：边界稳定 → 渲染结果逐字节一致 → prompt cache 的前缀能命中。每轮微调会让缓存天天失效。

### 中文 token 估算

不能用"4 字符/token"（英文口径），中文约 **1 字 ≈ 1 token**，否则会低估约 4 倍。

**反方理由**：按块预算 + 三层渲染实现成本明显高于"超 70% 就摘要"；如果对话普遍不长，这套可能永远用不上。

**你的选择**：____B__

## M3 · 指代消解做不做

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 每轮都做** | 每轮调 LLM 改写（指代 + 口语归一合并） | 意图和检索都拿到完整句；行为可预测 | 每次多一次调用，+300~800ms |
| B. 按需触发 | 规则检测指代词/短句才改写 | 省调用 | 规则漏检时会跳过 |
| C. 不做 | 用原句 | 零成本 | "那单""这个"无法处理 |

**推荐：先 A（每轮），用评测验证后再决定是否降到 B**

**理由**：意图是"阀门"——判成"商品咨询"走检索、判成"退款"走规则。**阀门错了，后面做得再对也没用。** 所以值得在它之前花一次调用，把句子补完整。

### 参考实现做了四层改写（对照）

| # | 位置 | 做什么 | 触发 | 失败 |
|---|---|---|---|---|
| ① | 每轮入口 | 指代消解 + 口语归一（**合并成一次调用**） | 每轮 | 返回原句 |
| ② | 知识检索前 | 口语→标准问法 + 同义词扩展 | 知识路 | 回落原问题 |
| ③ | 退款政策检索 | 生成 3 条检索友好查询，多路去重 | 仅退款流程 | 回落 `[原句]` |
| ④ | 意图分类 | 不改写，但带历史判"意图漂移" | 每轮 | 归"其他" |

**我们只做 ① 就够**：②③ 属于检索侧优化，可以等 hit@3 不达标再上（与数据文档里"检索三段式"同一个判断逻辑）。

### 三条落地约束

**① 单一来源**

```python
resolved_query = await coref.resolve(query, history)
# 意图分类、检索、退款判定都用它；下游不许再改写
```

意图 prompt 里要明确写："输入已是指代消解后的完整问题，只管判意图、不要再改写。"

**否则每一层都改一遍，最后越改越偏。**

**② 每层失败降级到上一层输入**

```
改写失败 → 用原句（不阻断）
扩展失败 → 用原句检索
多 query 失败 → 至少留一条
```

改写是"让检索更好命中"，不是"检索的前提"。

**③ 留痕区分改了没改**

```python
mode = "rewrite" if resolved != query else "passthrough"
```

**如果 trace 里长期全是 passthrough**，说明改写没起作用，该查 prompt 或该关掉。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 改错实体（上文有两笔订单，"那单"补错） | state 里同时保留 `raw_query` 与 `resolved_query` |
| 单点故障：改写错 → 意图和检索一起错 | 意图置信度低时，用原句再判一次；两次不一致 → 追问用户 |
| 调试困难 | trace 存改写前后两句 |
| 花了成本没收益 | **用评测验证**（见下） |

### 怎么验证有没有用（用 EvalFlow）

```
同一批 40 题
  A 组：带改写 → 记 hit@3、意图准确率
  B 组：不带改写 → 同一批题再跑
对比：提升 >5% 才留，否则关掉
```

**很多项目加了改写却从不验证。** 你能验证，这就是差异。

**反方理由**：每轮一次调用是实打实的成本；如果用户输入本来就规范（表单/按钮式），改写纯属浪费。可以先看一周线上日志，`passthrough` 比例超过 70% 就该改成按需触发。

**你的选择**：___A___

## M4 · 跨轮状态存什么

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 只靠 checkpointer | 图状态里带流程信息 | 不用额外设计 | **前端查不到**"你有未完成的退费" |
| **B. DB 存锚点 + checkpointer 存图状态** | 会话表加 3 个字段 | 前端可展示、可恢复 | 两处状态要同步 |
| C. 前端存 | localStorage 保存进度 | 不占后端 | 换设备就丢，不可信 |

**推荐：B**

会话表加三个字段：

| 字段 | 内容 | 用途 |
|---|---|---|
| `active_flow` | `refund` / `price_protection` / `null` | 判断有没有进行中的流程 |
| `pending_question` | `order_id` / `confirm` / `null` | 知道在等什么 |
| `draft` | 已收集的要素（JSON） | 用户补充后继续算 |

**为什么不只靠 checkpointer**：前端要显示"您有一笔未完成的退费申请"，必须能查 DB。

**反方理由**：两处状态要同步，容易出现"DB 说在等订单号、图状态已经结束"的不一致；需要在流程结束时清理这两处。

**你的选择**：__B____

## M5 · 用户中途改话题

> **先分清两种"挂起"**
>
> | 术语 | 含义 | 谁停住了 |
> |---|---|---|
> | **执行挂起（interrupt）** | 图暂停，等前端回填，`Command(resume)` 继续 | 程序停住 |
> | **状态挂起（park）** | 程序继续跑，把未完成流程存进业务表 | 什么都没停 |
>
> **本节说的是 park；M6 的 resume 说的是 interrupt。**

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 暂停保留（park）** | 存 `active_flow` / `pending_question` / `draft`，正常回答新问题，结尾问"要继续吗" | 用户不用重来 | 状态复杂，需要超时清理 |
| B. 丢弃重置 | 新问题覆盖旧流程 | 简单 | 用户要重来，弃单率高 |
| C. 强制先完成 | 先答完当前流程才处理新问题 | 流程完整 | 用户会觉得"它不听我说话" |

**推荐：A（park）**

### park 具体存什么

```
用户：我要退，尺寸不合适        → draft.reason = 尺寸不合适
系统：请提供订单号               → pending_question = order_id
用户：等等，你们几点上班？
```

**park 就是存下这三个字段，然后正常回答营业时间：**

```json
{
  "active_flow": "refund",
  "pending_question": "order_id",
  "draft": { "reason": "尺寸不合适", "product": "ST-60" }
}
```

**用户回来说"继续退费"时：**

```
active_flow = refund      → 知道要做什么
draft        = {...}      → 知道已填了什么
pending_question = order_id → 知道还缺什么
→ 直接问「请提供订单号」，不用重来
```

### 与 interrupt 的配合（顺序很重要）

真实场景里两个都要用：

```
需要结构化交互（选订单）时
  ① 先把 draft 落库（park）
  ② 再 interrupt 弹选择器
```

**为什么必须先写库再中断**：`interrupt` 恢复时会**从头重跑节点**（附录 A3），如果"写库"和"interrupt"在同一节点里，resume 会写两次。

**两种正确写法**：

| 做法 | 说明 |
|---|---|
| **拆成两个节点** | 节点 A 写 draft（普通节点），节点 B 只做 interrupt |
| **同一节点但写操作幂等** | 用 upsert（按 conversation_id + flow 唯一） |

**没有 park 的后果**：参考实现只有 interrupt，没有 park——用户不选订单、改问别的，上一轮的进度就丢了（`order_id` / `order_data` 每轮被重置）。

**反方理由**：park 后如果用户一直不回，会留下僵尸会话；必须配 M7 的超时清理。

**你的选择：A（暂停保留 / park）**

## M6 · 追问挂起后，下一句怎么接

> 这里的「挂起」指 **执行挂起（interrupt）**：图停住了，等用户回填。
> 与 M5 的 park（进度存起来、程序继续跑）不是一回事。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 全部走 resume | 前端把回复转成 resume value | 流程精确 | 用户说"算了吧"就没法映射 |
| **B. 新 turn 为主 + 结构化 resume 兜底** | 自然语言走正常流程，靠 `pending_question` 接回；结构化输入（选单）走 resume | 贴合真实用户 | 分类要多识别一类"补充信息" |
| C. 全部走新 turn | 不区分 | 统一 | 订单选择器这类结构化交互用不上 |

**推荐：B**

判断顺序：

```
收到新消息
  ├─ 前端带 resume_value（用户点了订单选择器）→ 走 Command(resume)
  └─ 纯自然语言 → 走新 turn
       ├─ pending_question 非空 且 意图=补充信息 → 接回原流程
       └─ 否则 → 正常分流
```

### 落地方式：槽位填充优先，不占用意图分类

**"新 turn 为主"不等于"让意图分类识别补充信息"**——那会污染意图体系（"1001" 在别的场景下可能是订单查询）。

正确做法：

```
收到消息
  ├─ pending_question 非空？
  │    ├─ 是 → 试着从这句话抽该槽位（规则优先，抽不到再 LLM）
  │    │        ├─ 抽到      → 填 draft，接回原流程
  │    │        └─ 抽不到    → 按新话题处理（park，见 M5）
  │    └─ 否 → 正常分流
  └─ 识别到"取消/算了" → 清空 active_flow / draft，正常回话
```

**理由**：槽位填充是"针对当前问题抽值"，判定简单可靠；塞进意图分类会让意图体系变脏。

**风险**：抽不到时要能正确 fallback 到"新话题"，否则用户问别的会被强行塞进流程。

**反方理由**：两条路径增加实现和测试成本；如果只有订单号一种追问，A 也能接受。

**你的选择**：____B__

## M7 · 挂起状态多久失效

| 选项 | 做法 | 说明 |
|---|---|---|
| **A. 30 分钟** ✅ | 超时清空 `active_flow` / `pending_question` / `draft` | 接近"一次咨询"的自然边界 |
| B. 24 小时 | 更宽松 | 僵尸会话堆积 |
| C. 不失效 | 永久保留 | 用户下次进来会看到半年前的未完成单 |

**你的选择：A（30 分钟）**

理由：与"一次咨询"的自然边界接近；单值、一个计时器，实现最简。

**必须配一条 UI 提示**（低成本、解决"用户不知道有时限"）：

```
用户挂起退费时，界面显示：
「本次申请保留 30 分钟，超时需重新发起」
```

**已知短板**：用户去翻订单号、问家人，可能超过 30 分钟——回来要重来。

**回看条件（写进后续优化）**：

```
上线后如果「恢复率低」或「用户抱怨要重来」占比 > 20%
→ 延长到 2 小时，或拆成两个计时器（上下文 30 分钟 / 草稿 24 小时）
```

**反方理由**：30 分钟对真实用户偏短；电商客服里用户隔几小时回来很常见。但这个项目当前没有真实用户，先简单，等有数据再调。

## M8 · 同一会话并发两条消息

| 选项 | 做法 | 风险 |
|---|---|---|
| **A. 按会话串行** | 加锁或队列，第二条排队 | 需要锁实现；等待过久要拒绝 |
| B. 允许并发 | 两条同时跑 | 同时读写同一 thread，状态互相覆盖 |
| C. 拒绝第二条 | 直接返回"上一个请求处理中" | 体验差，但实现最简 |

**推荐：A**

- 锁等待上限 5s，超时返回"上一条还在处理中"
- 锁粒度 = `conversation_id`

**反方理由**：单人项目可能永远不会遇到并发；加锁会增加一处故障点。但**如果没有锁，一次误触就能重现"状态被覆盖"的诡异 bug**。

**你的选择**：___A___

## 后续优化（暂不做，触发条件到了再上）

| 项 | 内容 | 触发条件 | 预计成本 |
|---|---|---|---|
| **查询改写 + 同义词扩展**（M3 ②） | 口语→标准问法，产出同义词用于 BM25 | 知识类问题 **hit@3 < 0.8** | 半天的 prompt + 评测 |
| **多 query 扩写**（M3 ③） | 生成 3 条检索友好查询，多路检索后去重合并 | 退款政策问题 hit@3 明显低于其他桶 | 1 天 |
| **三层渲染的层 2**（M2） | 工具结果半压（而非直接压成一行） | 对话逾 20 轮、或工具返回普遍 >500 字 | 1 天 |
| **摘要段的语义筛选** | 只注入与当前问题相关的摘要段 | 摘要段超过 5 段、注入后明显挤占窗口 | 1 天 |
| **挂起时长调整**（M7） | 30 分钟 → 2 小时，或拆成两个计时器 | 恢复率低 / 用户抱怨要重来 >20% | 半天 |

**为什么单独列：**这四项都是"锦上添花"，不做也能跑，但**忘了就永远不做**。等指标触发时，从这里直接取。

**判断依据统一**：先测（hit@3 / 覆盖度），不达标再上——与数据文档里"白话摘要先测再加"同一个逻辑。

## 确认清单

- [x] **M1 消息存储：B** —— DB 存全量（可回放）+ 送模型时窗口裁剪（控成本）；消息带 `db-{id}` 锚点。
- [x] **M2 窗口与摘要：B** —— 滑窗 + 滚动摘要；预算按块分配（系统提示/证据/摘要/输出预留/滑窗）；工具结果超 200 字符压缩；边界一次挪到位保护 prompt cache。
- [x] **M3 指代消解：A** —— 每轮都做（指代 + 口语归一合并一次调用）；理由：意图是阀门，阀门错了后面全错。后续用 EvalFlow 做 A/B，验证是否可降级为按需。
- [x] **M4 跨轮状态：B** —— DB 存 `active_flow` / `pending_question` / `draft`，checkpointer 存图状态；前端要能查"未完成申请"。
- [x] **M5 中途改话题：A（park）** —— 存 `active_flow` / `pending_question` / `draft`，回答新问题后提示「要继续吗」；参考实现没有 park，用户改话题回来就得重来。
- [x] **M6 接回方式：B** —— 新 turn 为主（槽位填充接回）+ 结构化 resume 兜底（选单/确认）。
- [x] **M7 挂起失效：A（30 分钟）** —— 配 UI 提示；回看条件：恢复率低或抱怨重来 >20% 再调整。
- [x] **M8 并发控制：A** —— 按会话串行，锁等待 5s；前端流式期间禁用发送作为第一道防线。

**八条全部确认。** 落地顺序建议：M1/M4（存储与锚点）→ M3（指代）→ M6/M5（接回与 park）→ M7/M8（清理与锁）→ M2（预算与摘要）。
