# 电商客服 Agent · 意图与出口设计

> 状态：设计稿（2026-10-26），先定分类与路由，再写状态机与代码。
> 下游：[数据与知识库设计](./电商客服-数据与知识库设计.md)
> 原则：**出口按「处理方式 + 失败处理」分，不按业务主题分。**

---

## 一、判定原则

两条，够用：

1. **处理方式不同 → 拆**
2. **失败处理方式相同 → 合并**

出口不是"业务分类"，是"系统具备的几种处理能力"。
所以意图可以有 12 个，出口只有 5 个。

---

## 二、五个出口

| 出口 | 处理什么 | 失败了怎么办 | 典型意图 |
|---|---|---|---|
| **A 知识回答** | 政策、规格、活动规则、会员权益 | 证据不足 → 兜底，不硬答 | 政策问答、商品规格 |
| **B 数据查询** | 订单、物流、库存、价格 | 查不到 / 无权限 → 明确告知，不猜 | 订单查询、库存价格 |
| **C 规则处理** | 退款资格、价保补差、订单变更 | 条件不满足 → 说明原因；规则冲突 → 转人工 | 退款、价保、变更 |
| **D 转人工** | 投诉、超权限、资金异常 | 建单失败 → 兜底并给人工入口 | 投诉 |
| **E 兜底** | 闲聊、无关问题、无法处理 | 引导到可用能力 | 闲聊、其他（默认值） |

**关键**：五个出口的差异不在"管什么业务"，在"失败了怎么办"。

### 「其他」不是第 13 个意图

它是**分类失败时的默认值**：

```
模型越界 / 解析失败 / 置信度过低 → 「其他」→ E 出口
```

```python
INTENTS = (...12 个...)
intent = result if result in INTENTS else "其他"
```

## 四、四对易混意图的边界规则

| 易混对 | 边界规则 |
|---|---|
| 商品规格 vs 库存价格 | 问「是什么 / 支持什么」→ 规格；问「有没有 / 多少钱」→ 库存价格 |
| 订单查询 vs 物流查询 | 有物流单号或问「到哪了」→ 物流；问「状态 / 金额」→ 订单 |
| 退款申请 vs 订单变更 | 涉及退钱 → 退款；只改信息（地址 / 收货人 / 发票）→ 变更 |
| 政策问答 vs 优惠券活动 | 涉及具体券 / 具体活动名 → 优惠券；通用规则 → 政策 |

**不做这四条规则，12 类里至少 4 类会互相吞。**

---

## 五、判定顺序（分流不是平行的）

```
1. 兜底判定   明显无关 / 超范围 → 直接拒，不检索不调工具
2. 风险判定   投诉 / 情绪 / 涉资金 → 优先转人工
3. 方式判定   知识 / 数据 / 规则 → 正常分流
```

**为什么先判兜底和风险：**

- 兜底先判：无关问题不进检索，省一次调用
- 风险先判：投诉类即使查得到答案，也不该用标准话术回

## 六、兜底出口内部分三个脚本

```
E 兜底
  ├─ 社交回应   「你好 / 谢谢 / 在吗」→ 自然接话
  ├─ 确认致谢   「好的 / 明白了」→ 保持上下文，不换话题
  └─ 无法处理   「超出范围」→ 说明边界 + 引导
```

**出口一个，脚本三个。** 分开是为了回应得体，合并是为了不让路由表膨胀。

### 一个必测的坑

> 「你好，我想问下退款怎么弄」

按"含问候语"判闲聊 → 错。
**规则：业务关键词优先，问候语忽略。**

## 七、证据不足时怎么兜底

> 适用于 **A 出口（知识回答）证据不足**。数据查询失败、规则冲突各有自己的话术，见状态机文档的错误码。

### 为什么不在兜底时调模型

```
正常路径：有证据 → 模型组织语言 → 有据可依
兜底路径：没证据 → 模型组织语言 → 只能编
```

**兜底是幻觉最高发的时刻。** 在"证据不足"时再让模型说话，等于把最不可靠的环节交给最会编的组件。

三个附带收益：延迟为零、行为确定（可测试）、不会二次伤害。

### 三个方案

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A 固定话术 | 常量字符串 | 零成本、确定 | 生硬，无法解释原因 |
| B LLM 生成 | 让模型写"抱歉没找到…" | 自然 | **最容易编**，多一次调用 |
| **C 模板 + 变量** | 固定骨架 + 填空 | 零模型、又有信息量 | 需设计槽位 |

**选择 C。**

### 模板结构

```python
FALLBACK_TEMPLATE = (
    "关于「{topic}」，我这边没有找到确切的依据，不能给您结论。"
    "已经为您记录，{next_step}"
)
```

| 槽位 | 来源 | 约束 |
|---|---|---|
| `topic` | 从用户 query 截取关键词 | **不是模型生成** |
| `next_step` | 二选一：转人工 / 「您是不是想问『{top1_title}』」 | 固定句式 |
| `top1_title` | 检索返回的第一条标题 | 有依据的引导，不是瞎猜 |

### 必须做的两件事

**① 落池**：把问题、来源、置信度信号、召回快照写进低置信表（飞轮入口，详见 [数据飞轮设计](./电商客服-数据飞轮设计.md)）。

**② 给可点击动作**：不能只说"请联系人工"，必须同时给 `transfer_human` 动作，让前端渲染按钮。

### 召回快照三态（重要）

| 值 | 含义 | 该做什么 |
|---|---|---|
| `[...]` | 走了检索，有召回但分数低 | 调阈值或改检索策略 |
| `[]` | 走了检索，**零命中** | **补知识库**（真缺内容） |
| `null` | 没走检索（非知识路兜底） | 不是知识缺口，别误判 |

**「零命中」和「召回了但不够好」是两回事**，混在一起会导致补错东西。

### 如果一定要用 LLM，三条约束

1. 只许说两件事："没找到" + "下一步怎么办"，不许给业务结论
2. 输出结构化：`{"action": "clarify"/"transfer"/"suggest", "hint": "..."}`
3. 引导候选只能从检索 top-k 标题里挑，不能自己造

**本质：让模型做措辞，不做判断。**

## 九、与 MewHelp 的差异（面试可讲）

| MewHelp | 本设计 | 差异理由 |
|---|---|---|
| `business` 一个出口管「订单 / 物流 / 人工」 | **B 数据 + D 转人工** 拆开 | 查数据失败是"查不到"，转人工失败是"建单失败"，失败处理不同 |
| 意图按"业务主题"分 | 按"处理方式"归并 | 主题分 12 类，处理方式只有 5 种 |
| 无价保 / 无订单变更 | 有 | 规则+状态依赖，是更好的考点 |
| 商品咨询混在一起 | 规格（A）+ 库存价格（B） | 库存是实时数据，走检索会被闸门误拦 |

## 十、落地顺序

```
第 1 周：先做 8 类意图跑通
  政策问答 / 商品规格 / 订单查询 / 物流查询
  库存价格 / 退款申请 / 投诉 / 闲聊

第 2 周：补 4 类
  优惠券活动 / 会员权益 / 价保申请 / 订单变更
  → 每加一个，补 3 条易混样本
```

**加的过程就是迭代故事**："第一版 8 类，发现价保和退款老混，所以拆出来单独建类。"
