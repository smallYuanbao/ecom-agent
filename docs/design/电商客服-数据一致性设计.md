## 背景：这个系统有几份"同一件事"

```
知识库文档（md）  ──切分──►  向量库 chunks
        │                        ↑
        └──飞轮写回──► FAQ 表 ───┘
                         │
                    评测集基线 ──► 指标

用户消息 ──► 图执行 ──► 工单/退款 ──► 会话状态
   ↑                                      │
   └──────────  回放 / 审计  ◄────────────┘
```

**每一对箭头都是"两处要保持一致"的地方**，也就是六个可能不同步的点。

## K1 · FAQ 写回后，向量库怎么同步

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 同步双写 | 审核通过 → 写 FAQ 表 → 立即写向量库 | 实时可见 | 向量库失败就不一致，且拖慢审核 |
| B. 定时全量重建 | 每天重建索引 | 简单、可对账 | 新知识当天搜不到 |
| **C. 写库为准 + 异步同步 + 对账** | 先写 FAQ 表（含 `sync_status`），后台任务同步，定时对账 | 一致性好、失败可重试 | 需要状态机与对账任务 |

**推荐：C**

```
审核通过 → INSERT FAQ (sync_status='pending')
        → 后台任务 upsert 向量 → sync_status='synced'
        → 失败：保持 pending，定时重试（指数退避）
        → 对账任务：DB 里 synced 但向量库没有 → 补写
```

**核心原则**：**向量库是派生数据，删了可以重建；数据库才是真相。**

**反方理由**：异步意味着有几秒到几分钟的延迟，用户刚补的知识可能还搜不到；同步双写虽然脆，但"立刻可见"。

**你的选择：C** —— 写库为准 + 异步同步 + 对账。审核通过先写 FAQ（`sync_status=pending`），后台同步向量库，失败重试，定时对账。**向量库是派生数据，数据库才是真相。**

## K2 · 知识库更新后，缓存怎么失效

> **当前决策：暂不做 RAG 缓存**，因此本条**暂不适用**，进后续优化。
> 下面保留设计，等真做缓存时直接取用。

RAG 结果通常有缓存（同样的 query 不必重复检索）。**不做缓存，就没有失效问题**——每次重新检索，天然一致。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 版本号命名空间** | 缓存 key = `{kb_version}:{user_id}:{query_hash}:{top_k}`，知识库更新则版本 +1 | 不用逐条删，自然失效 | 一次更新全量失效 |
| B. 逐条精准删除 | 找出受影响的 query 删缓存 | 命中率高 | 实现复杂，几乎不可能做对 |
| C. 设短 TTL | 5–30 分钟自动过期 | 简单 | 更新后最长等 TTL |

**若将来做缓存，推荐 A。**

### 做缓存时必须遵守（提前记下，避免将来越过安全设计）

```python
# 错的：只按 query 缓存 → 用户 A 的结果被用户 B 命中
key = hash(query)

# 对的：必须带版本、身份、参数
key = f"{kb_version}:{user_id}:{hash(query)}:{top_k}"
```

| 要素 | 为什么 |
|---|---|
| `kb_version` | 知识库更新后旧缓存自然失效 |
| `user_id` | **不加会跨用户泄露**（绕过 S1/S2 的隔离） |
| `top_k` / 过滤条件 | 参数不同结果不同 |

**只做检索结果缓存，不做回答缓存**——回答里可能含个人信息，复用风险更高。

**反方理由**：不做缓存意味着每次都要重新检索，高频问题会重复消耗 embedding 和 rerank 的延迟与成本。

**你的选择**：暂不做缓存（进后续优化）

## K3 · 跨表事务

一次退费可能同时写：`messages`（问答）、`tickets`（工单）、`conversations`（状态清理）、`audit`（留痕）。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 单事务全包 | 一个事务写完所有表 | 强一致 | 长事务；外部调用（退款接口）不能进事务 |
| **B. 主表事务 + 最终一致** | 核心表一个事务，附属表异步/幂等补齐 | 短事务、可重试 | 需要补偿逻辑 |
| C. 不保证 | 各写各的 | 简单 | 出现"有工单没消息"的脏数据 |

**推荐：B**

```
事务内：写 messages（用户+助手） + 更新 conversations.active_flow
事务外：建工单（外部系统）→ 用 request_id 幂等
       写 audit → 失败只记日志，不影响主流程
```

**关键**：**外部调用永远不能放进数据库事务**——事务回滚不了别人家的系统。

**反方理由**：最终一致意味着有一小段时间"消息有了、工单还没建"，用户查询可能看到中间态。

**你的选择：B** —— 主表事务 + 最终一致。核心表一个事务；外部调用（建单/退款）在事务外，靠 `request_id` 幂等；audit 失败只记日志。**外部调用永远不能放进数据库事务。**

## K4 · 幂等写入（数据库层）

前面 C6（client_message_id）和 D11（request_id）定的是"接口层"，这里定"数据库层怎么兜住"。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 唯一索引 + 冲突查回** | `INSERT ... ON CONFLICT DO NOTHING`，再查一次返回已有结果 | 数据库保证，绝对可靠 | 需要设计幂等键 |
| B. 先查后写 | `SELECT` 有就返回，没有就 `INSERT` | 简单 | 并发下会重复插入 |
| C. 只靠应用层去重 | 内存 set / Redis | 快 | 重启丢失、多实例失效 |

**推荐：A**

```sql
CREATE UNIQUE INDEX uk_msg_idem ON messages(conversation_id, client_message_id);
CREATE UNIQUE INDEX uk_ticket_idem ON tickets(request_id);
```

**写入流程**：

```
INSERT ... ON CONFLICT (conversation_id, client_message_id) DO NOTHING
  → 影响行数 = 1：首次，继续处理
  → 影响行数 = 0：重复，查回已有记录直接返回
```

**反方理由**：幂等键要长期保留，表会变大；需要定期归档。

**你的选择：A** —— 唯一索引 + 冲突查回。`UNIQUE(conversation_id, client_message_id)` / `UNIQUE(request_id)`；`INSERT ... ON CONFLICT DO NOTHING` 后查回已有记录返回。

## K5 · 软删除与知识溯源

这一条其实是两件事，必要性差别很大：

| 子项 | 必要性 | 说明 |
|---|---|---|
| 软删除 | **低** | 单人项目误删概率低；但字段成本为零 |
| 删除审计（谁删了什么） | **很低** | 单人项目没有"谁"，信息量为零 |
| **知识溯源（知识从哪来）** | **中高** | 飞轮依赖它，否则查不清一条知识的来路 |

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 最小版** | `deleted_at` 字段 + FAQ 来源字段 | 成本低，覆盖真需求 | 没有完整审计表 |
| B. 完整审计表 | 独立 `audit_log`，记录所有增删改 | 可追责 | 单人项目信息量低、维护成本高 |
| C. 物理删除 | 真删 | 干净 | 无法回放 |

**推荐：A（最小版）**

### 现在做

**① 软删字段**

```sql
ALTER TABLE conversations ADD COLUMN deleted_at DATETIME NULL;
-- 列表查询统一加 WHERE deleted_at IS NULL
```

**② 知识条目来源字段**（这才是关键）

```sql
faq (
  id, question, answer,
  source_type,         -- 'flywheel' / 'manual'
  source_question_id,  -- 来自哪条低置信问题
  reviewed_at,         -- 审核时间
  kb_version           -- 进的是哪个版本
)
```

**为什么需要**：三个月后你要能回答「这条知识是哪个原始问题带来的、什么时候进的库」。**没有这个，飞轮就是黑盒。**

### 不做

| 不做 | 原因 |
|---|---|
| 独立审计日志表 | 单人项目没有"谁"，记了也没人看 |
| 冷存储归档 | 数据量远没到 |
| 物理删除 | 软删够用 |

### 一个能加分的认知：删除权 vs 留存

真实业务里这两个是冲突的：

```
用户：「删除我的数据」
合规：「我们有义务保留交易记录 X 年」
```

**标准解法是「脱敏删除」**：保留记录结构与统计价值，抹掉可识别信息（手机号、地址），而不是整行删掉。

**你不用实现，但知道这个冲突本身就值钱**——被问到「用户要删数据怎么办」，答"脱敏保留"比"直接删"专业得多。

**反方理由**：最小版没有完整的变更历史，如果知识被误改，查不到是谁改的；但那是多人协作才需要的能力。

**你的选择：A（最小版）** —— `conversations.deleted_at` + FAQ 来源四字段（`source_type` / `source_question_id` / `reviewed_at` / `kb_version`）；不做独立审计表、不做冷存储归档。

## K6 · 知识库版本与评测基线

知识库一改，历史评测分数就不再可比——这和 EvalFlow 的 `dataset_hash` 是同一个问题。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 哈希 + 版本 + 规模** | 评测快照记录 `dataset_hash` / `kb_version` / 规模指标 | 精确判断可比性 | 要维护版本号 |
| B. 不记录 | 直接比分数 | 简单 | 会得出错误的"变好/变差"结论 |
| C. 每次改库后强制全量重跑 | 保持可比 | 数据干净 | 成本高 |

**推荐：A**

### 参考实现怎么做的（对照）

它只记了**规模**，没记**内容指纹**：

```python
meta = {"n_samples": len(samples), "kb_chunks": await _kb_chunks()}
```

| 情况 | chunk 数 | 内容 | 能发现吗 |
|---|---|---|---|
| 加了一篇文档 | 变多 | 变了 | ✅ 数字不同 |
| **改了一篇文档内容** | **不变** | 变了 | ❌ **发现不了** |
| 删一篇加一篇 | 不变 | 变了 | ❌ 发现不了 |
| **评测集换了一批题** | 不变 | 变了 | ❌ **完全不知道** |

**根因**：它没有"一次 run"的概念——`eval_ch04` / `eval_ch05` / `eval_ch08` 各跑各的、各出一份报告，人工看，天然不存在"两次比较"。

**所以它不是没做好 K6，是没遇到这个问题**（没有统一评测平台）。

### 推荐方案：哈希管内容，规模管直觉

```json
{
  "run_id": 42,
  "dataset_hash": "51f2835e",
  "kb_version": "2026-10-28-a",
  "n_samples": 40,
  "kb_chunks": 52,
  "threshold": 0.6
}
```

| 字段 | 作用 |
|---|---|
| `dataset_hash` | 评测集内容指纹（覆盖问题/期望要点/分桶） |
| `kb_version` | 知识库内容指纹 |
| `n_samples` / `kb_chunks` | **快速直觉**：连数量都不一样，不用看内容就知道不可比 |
| `threshold` | 阈值变了，分数也不可比 |

**哈希和规模不重复**：哈希是精确判断（内容相同才算相同），规模是一眼判断（数量不同一定不同）。

### 规则

```
两次 run 的 dataset_hash 不同  → 评测集换了，分数不可比
两次 run 的 kb_version 不同    → 知识库变了，只能看趋势，不能算回归
两次 run 的 threshold 不同     → 判定标准变了，同样不可比
```

**判定逻辑与 EvalFlow 的 `dataset_comparability()` 完全一致**——你已经实现过一次，直接搬。

**反方理由**：多两个要维护的指纹（数据集 + 知识库）；忘了更新就白做。**缓解**：`kb_version` 用内容哈希自动生成，不靠人工递增。

**你的选择：A** —— 评测快照记 `dataset_hash` + `kb_version` + `n_samples` / `kb_chunks` + `threshold`；哈希管内容、规模管直觉；判定逻辑复用 EvalFlow 的 `dataset_comparability()`。
