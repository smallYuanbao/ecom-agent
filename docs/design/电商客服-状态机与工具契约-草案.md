## D0 · 图怎么组织（最基础的决策）

| 选项 | 做法 | 优点 | 缺点 |

**反方理由**：单图在小系统里更简单；子图会引入"状态在主图与子图之间传递"的复杂度，容易漏字段。

## D1 · C 出口（规则处理）分几个状态

| 选项 | 状态数 | 说明 |
|---|---|---|
| A | 5 | 抽取 → 校验 → 计算 → 合规 → 应答 |
| B | 7 | 上面 5 个 + `intake`（接收/必填校验）+ `need_info`（追问补信息） |
| **C** | **8** | B + 把 `query_data` 从 `compute` 拆出来（查数据独立） |
| D | 9 | C + `review`（结果复核） |

**推荐：C（8 个）**

四条理由：

1. `need_info` 必须独立——它是**可中断点**，用户退出后要能从这里恢复
2. `intake` 独立——在调模型前就挡掉缺字段的请求，省一次 LLM 调用
3. **`query_data` 独立**——失败处理不同：查不到要引导补单号，算不出要转人工；重试策略也不同（工具要重试，计算不用）
4. **`review` 暂不加**——除非你能立刻写出三条可执行的复核规则，否则它是个空节点

**反方理由**：

- 7 个更简单（12 条边），但 `compute` 要同时处理"查不到"和"算不出"两种失败，测试与重试逻辑混在一起
- 9 个可测性最好，但边数涨到 20+，且 `review` 没有规则支撑时会变成走过场

**你的选择**：__C____

## D2 · 哪些检查做成「守卫」（代码硬判断）

| 选项 | 做法 | 风险 |
|---|---|---|
| A. 全部校验都做守卫 | 每个字段、每条规则都硬判断 | 状态与转移膨胀，规则变更要改图 |
| **B. 只做高风险守卫** | 合同要素、金额、权限、红线 | 低风险项交给模型判断，可能不一致 |
| C. 不做守卫 | 全部交给模型 | 等于放弃可靠性 |

**推荐：B**

理由：守卫的价值是"挡住模型不该决定的事"。低风险项（如语气、措辞）交给模型无害；高风险项（金额、权限、合规）必须代码说了算。

**反方理由**：分级标准本身需要判断——什么算高风险？如果分错，低风险项会变成事故。

**你的选择**：___B___

## D3 · 追问补信息怎么实现

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 独立状态 `need_info`** | 统一一个状态处理所有"缺信息"，补完回原状态 | 图上可见、可单测、追问逻辑集中 | 多 1 状态 + 2 条边；需记录"回到哪个状态" |
| B. 节点内循环（无中断） | 当前节点 while 循环里问 | 实现最短 | **无法跨请求恢复**（用户退出即丢） |
| C. 不做 | 缺信息直接转人工 | 最简单 | 体验差，弃单率高 |
| **D. 节点内循环 + interrupt** | 循环里 `interrupt()` 挂起，resume 回填（**参考实现的真实做法**） | 不加状态和边，且**能跨请求恢复** | 追问分支在图上看不见；不可单测；节点会从头重跑（写操作须幂等） |

**推荐：A**

理由：

1. **追问逻辑集中**——所有"缺什么问什么"都在一个节点，不用每个节点各写一套
2. **图上可见**——排查时能看到"卡在追问"，而不是节点内部的黑盒
3. **可单测**——给定缺失列表，断言话术与期望字段即可

**反方理由（支持 D）**：

- D 同样能跨请求恢复，而且不加状态、不加边，图更简单
- 如果追问场景很少（只有订单号一种），为此多一个状态确实不划算

**什么时候改选 D**：只有 1–2 种固定缺失项、且前端不需要统一的追问组件时。

> **更正**：参考实现不是"B 的变体"。它有 `interrupt`，所以能跨请求恢复——**B 的核心缺点它没有**。它属于选项 D。

**你的选择**：___A___

## D4 · 失败时的默认动作

| 选项 | 做法 | 代价 |
|---|---|---|
| A. 一律转人工 | 任何异常都建工单 | 人工成本高 |
| **B. 分级** | 缺信息→追问；规则冲突→转人工；系统异常→降级话术 | 判定标准要写清楚 |
| C. 一律拒答 | 不答就完了 | 体验最差 |

**推荐：B，但默认兜底是转人工**

理由：转人工是"有成本但不会错"，拒答是"零成本但会流失"。异常路径上宁可多花人工。

**反方理由**：分级需要一张明确的映射表，否则开发时会随手选一个，最后变成不可预测。

> **fail-closed：守卫自己失败时怎么办**
>
> 守卫也会坏——模型超时、JSON 解析失败、规则表读不到。这时候**不能"放行"**。
>
> | 场景 | 处理 |
> |---|---|
> | 守卫判断不了（异常 / 超时 / 解析失败） | **按不通过处理**（转人工或拒答） |
> | 读操作查不到 | 明确告知"没查到"，不算失败 |
> | 写操作任何异常 | 一律不执行，转人工 |
>
> 原则：**判断不了 ≠ 通过。** 放行的代价是编造或误操作，拦截的代价只是多一次人工。

**你的选择**：____B__

## D5 · 是否支持中断恢复

| 选项 | 机制 | 说明 |
|---|---|---|
| **A. 支持** | LangGraph checkpointer + thread_id | 用户退出后从断点继续 |

**反方理由**：需要设计状态序列化（哪些字段可序列化）、恢复时的幂等（避免重复调写操作）。

## D6 · 状态对象存什么

| 选项 | 内容 | 影响 |
|---|---|---|
| A. 全量中间结果 | 每次检索原文、每个工具返回 | 状态膨胀；每加一个字段就要在入口重置，漏一个就串轮 |
| B. 只存结论 + 引用 id | 金额、判定、引用条号 | 轻量可恢复；但下游节点可能要重复查库 |
| **B+（推荐）** | **结论 + 下游要用的结构化字段 + 引用 id** | 体积与可用性平衡 |
| C. 只存最终结果 | 一个答案字符串 | 无法调试与追溯 |

**推荐：B+**

三条理由：

1. **不选 A**：体积大（证据全文 2–3 KB，每次节点切换都序列化）、串轮风险高（每个标量都要记得重置）、状态里的数据可能是过期快照
2. **不选纯 B**：`compute` / `compliance` / `respond` 都需要结构化字段，只存 id 会导致一次请求多查三次库
3. **B+ = 存"下游要用的结论"，过程与原料进 trace**

### B+ 字段清单

| 存 | 不存 |
|---|---|
| `contract`：抽取后的结构化要素（型号 / 诉求 / 时间） | 用户原始长文本（已在 `messages`） |
| `order`：**归一化后的关键字段**（status / amount / paid_at） | 工具返回的原始 JSON |
| `refund_detail`：金额 + 分项明细 + 命中的规则 id | 计算过程的中间变量 |
| `violations`：触发的红线列表 | 全部规则的评估结果 |
| `citation_ids`：引用条号（如 `["第六条","第七条"]`） | 检索原文全文 |
| `decision`：通过 / 转人工 / 需补充 | — |
| `trace_id`：本次请求的留痕 id | trace 全量内容 |

**判断标准一句话**：下游节点要用得到的结构化结论留下，用不到的进 trace。

### 两条配套（选 B 或 B+ 都必须做）

**① 每轮重置清单**

```python
TURN_RESET = {
    "order": None, "refund_detail": None, "violations": [],
    "citation_ids": [], "decision": None, "trace_id": None,
}
```

**② 两轮串轮测试**

```
第 1 轮：走 C 出口（退款）→ 产生金额、明细、引用
第 2 轮：走 E 出口（闲聊）
断言：第 2 轮状态里不存在 refund_detail / violations
```

### 参考实现的做法（对照）

它选的是 **A**：状态里存 `evidence` 全文、`order_data` 整个 dict、`retrieved_snapshot` Top3 原文，
并在每轮入口写了一大段重置。注释原话：

> checkpointer 按 thread_id 持久化 State，这些无 reducer 的标量会跨轮残留（如上一轮闲聊/投诉的 answer、建工单可选项串到本轮），须在入口清零。

**这就是 A 的代价**：字段越多，重置清单越长，漏一个就串。

### 与 D5 的联动

| D5 选择 | 对 D6 的影响 |
|---|---|
| 支持恢复（checkpointer） | 状态每次序列化，**B+ 是唯一合理选择** |
| 不支持恢复 | A 也能跑，但串轮 bug 与持久化无关，仍建议 B+ |

## D10 · 写操作权限

| 选项 | 做法 | 风险 |
|---|---|---|
| A. 模型可直接调 | `create_ticket` 无确认 | 模型幻觉会建无用工单 |
| **B. 需用户确认** | 生成草稿 → 用户确认 → 执行 | 多一轮交互 |
| C. 禁止模型调用 | 由规则触发 | 灵活性差 |

**推荐：B**

**反方理由**：多一轮确认会降低自动化率；如果业务要求"零点击建单"，B 不适用。

### B 的落地细节（四条，参考实现验证过）

1. **参数不全时不弹确认卡**
   校验通过才 `interrupt({"type": "confirm_ticket", "preview": {...}})`；参数缺失交回引擎返回"校验拦下"，模型自然向用户追问。
   → 用户不会看到信息不全的确认卡。

2. **执行引擎再做一次门禁**
   ```python
   if spec.permission == "write" and not confirmed:
       return 拒绝执行
   ```
   节点层的判断可能被模型换条路径绕过，**引擎层是最后一道**。

3. **resume 值形状守卫**
   不是 `{"confirmed": true}` 的一律按未确认处理——宁可让用户重来，不让节点炸。

4. **确认之前不做任何副作用**
   `interrupt` 之前只做纯校验（呼应附录 A3：恢复会从头重跑节点）。

> **一个坑**：如果某个写操作**不走执行引擎**（例如被拦成前端表单），归属/权限校验必须**在拦截之前单独做**，否则它就是绕过校验的后门。参考实现里 `submit_refund` 就踩过这个点。

**你的选择**：__B____

## D12 · 超时与重试

| 选项 | 做法 | 说明 |
|---|---|---|
| **A. 分级：按错误类型 + 按工具** | 超时不重试；连接类错误重试 1 次；写操作一律不重试 | 既控延迟，又不丢抖动容错 |
| B. 统一 3s 不重试 | 简单 | 知识检索容易被误杀；一次网络抖动就失败 |
| C. 统一重试 2 次 | 容错强 | 超时重试让用户等成倍；写操作重试有资损风险 |

**推荐：A**

### 错误类型 × 重试策略

| 错误 | 读操作 | 写操作 | 理由 |
|---|---|---|---|
| **超时** | ❌ 不重试 | ❌ | 服务慢，重试只会再等一轮 |
| **连接失败 / 连接重置** | ✅ 重试 1 次 | ❌ | 瞬时故障可恢复；写操作重试可能重复执行 |
| **服务端 5xx** | ✅ 重试 1 次 | ❌ | 同上 |
| **参数校验失败** | ❌ | ❌ | 重试也一样错 |
| **业务错误（查不到 / 无权限）** | ❌ | ❌ | 这是有效结果，不是故障 |

**核心区分**：
- **超时** = "慢" → 重试无益
- **连接失败** = "断" → 重试常能恢复

### 分工具超时（不统一设 3s）

| 工具 | 超时 | 依据 |
|---|---|---|
| `query_order` | 2s | 单表查询，正常几十毫秒 |
| `query_stock` | 2s | 同上 |
| `query_logistics` | 3s | 可能要调外部物流接口 |
| 知识检索（含 rerank） | **5s** | 向量检索 + 重排更慢，3s 会频繁误杀 |
| `create_ticket`（写） | 5s | 不重试 |

**定值原则**：超时取"正常耗时的 3–5 倍"，不是统一值。

### 三条原则

1. **超时按工具定**，不搞全局统一值
2. **重试只针对"可能自己恢复"的错误**（连接、5xx），不针对"结果已确定"的错误（参数、业务）
3. **写操作一律 0 重试**，容错靠 `request_id` 幂等 + 用户手动重试

### 与参考实现的差异

它读操作默认允许重试，**且把超时也归进可重试类型**。我们更严：**超时不重试**。

理由：RAG 检索慢是常态，重试只会让用户等成倍，而成功率提升有限。

**反方理由**：分级策略配置项更多；超时不重试意味着偶发慢查询会直接失败。如果线上超时率 >2%，正确做法是**优化查询本身**（加缓存、加索引），而不是加重试。

# 附录 A：参考实现中值得借鉴的做法

> 来源：阅读参考项目的退款子流程（`app/graph/nodes.py`）。**借鉴的是做法，不是代码。**

## A1 · 用 interrupt 做追问（D3 的选项 D）

```python
while not owns_order(uid, oid):
    orders = list_user_orders(uid)
    oid = interrupt({"type": "select_order", "orders": orders})
```

| 维度 | 评价 |
|---|---|
| 优点 | 不新增状态和边；图保持简洁 |
| 缺点 | 追问逻辑藏在节点里，**测不到**；追问路径在图上看不见 |
| 与本设计的关系 | 我们倾向独立状态 `need_info`，因为要能单测和可视化 |

**取舍**：重视"图简单"选 interrupt；重视"可测试/可观测"选独立状态。

## A2 · 权限校验必须放进确定性节点

参考实现的注释原话：

> 归属校验放在这里而不是只放在工具里：退款子流程是确定性节点，不经 `agent_tools`，工具那道校验够不着。

**对本设计的硬约束**：

- B/C 出口走确定性节点，**不经过工具层**
- 所以 `query_order` 内部的归属校验**不够**
- `validate` 节点必须再做一次 `order.user_id == current_user`

**推论**：凡是绕开 Agent 的路径，权限都要在节点里再校验一遍。

## A3 · interrupt 之前只做只读

参考实现注释：

> interrupt 之前只做只读（resume 时本节点从头重跑）。

**机制**：LangGraph 恢复时**从头重跑整个节点**。

**对本设计的硬约束**（直接影响 D5 / D10 / D11）：

| 约束 | 说明 |
|---|---|
| 写操作不能放在 interrupt 之前 | 否则每次恢复都重复执行一次 |
| 任何可能被重跑的节点，写操作必须幂等 | 用 `request_id` 去重 |
| 节点内顺序：先只读 → 再 interrupt → 再写 | 反了就出事 |

**结论**：如果选 D3=interrupt 或 D5=支持恢复，**D11 幂等就不是可选项，是必选项**。

## A4 · 检索侧的三段式（可选）

参考实现在政策检索上做了三件事：

1. **Query 扩写 3 条**（原始 + 两条变体）
2. **多 query 分别检索 → 按 chunk id 去重 → 保留最高分**
3. **head/tail 排列**：把高分证据放在头尾，避免中间被忽略

**我们是否采用**：语料只有 30–50 chunk 时先不做；如果法规类问题 hit@3 < 0.8，再上这套。

## A5 · fail-closed：守卫自己失败时怎么办

参考实现 `selfcheck.py` 的注释原话：

> 模型异常按「证据不足」处理，不按「够用」放行……判不足最多是让用户看到兜底话术、多走一次人工，代价小得多。

**这个原则适用于所有守卫**，不只证据自评闸。

| 守卫 | 失败时的默认动作 |
|---|---|
| 证据闸（检索分数异常） | 按证据不足 → 兜底 |
| 自评闸（LLM 超时 / 解析失败） | 按不足 → 兜底 |
| 要素校验（规则表读不到） | 按缺失 → 追问或转人工 |
| 金额校验（计算结果异常） | 按不通过 → 转人工 |
| 写操作（任何异常） | 不执行 → 转人工 |

**唯一例外**：读操作查不到时，可以直接告知"没查到"，不必转人工——因为"查不到"本身是有效信息。

**反例（不要这么做）**：

```python
except Exception:
    pass          # 守卫失效还假装通过
```

这是最危险的写法：守卫挂了，系统却按"检查通过"继续跑。
