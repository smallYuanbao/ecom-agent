## 0. 30 秒版本

> 「B 出口做**订单查询、物流查询、库存价格**，是五个出口里唯一**完全不调模型**的。
> 它是一个 **5 状态确定性流水线**：抽参数 → 校验 → 查询 → 组装/追问。
>
> 参数用**正则 + 数据库匹配**，回答用**模板**，金额和库存逐字来自数据库。
> 模型只在上游做一次意图分类——因为它要判断"到哪了"是查物流还是查订单，
> 这部分是自然语言；进了 B 出口之后没有任何模型参与。
>
> 结果是端到端中位数 **0.98s**，比 C 出口（4.72s）快一个数量级；
> 代价是措辞不标准时只能追问，不能像 Agent 那样自己想办法。」

## 1. 核心取舍：为什么 B 出口不用模型

**结论**：能用确定性代码拿到唯一正确答案的地方，不让模型参与。

| 判据 | B 出口 | 结论 |
|---|---|---|
| 参数是什么 | 订单号（数字）/ SKU（`ST-20`）/ 规格（颜色） | 正则 + 数据库匹配足够 |
| 答案是什么 | 字段读数（状态、金额、轨迹、库存） | 模板输出更准 |
| 答错代价 | 报错金额 / 库存 = 用户直接损失 | 不让模型复述数字 |
| 失败怎么办 | 查不到就明说，用户能自己核对单号 | 不需要语言理解 |
| 步骤是否固定 | 是（抽参→校验→查→答） | 不需要 Agent 探索 |

**三个出口的分工**：

| 出口 | 模型做什么 | 为什么 |
|---|---|---|
| A 知识 | 组织语言 + 引用 | 政策是自然语言，答案需要解释 |
| **B 数据** | **只在上游做意图分类** | 参数与答案都是结构化的 |
| C 规则 | 抽要素 + 判资格 | 政策理解与责任判断需要模型 |

**可讲的取舍**：

> 「参考实现 MewHelp 在这里是让 Agent 自己选工具、自己组织回答。
> 我把它改成固定链 + 模板，两个原因：
> 一是数据查询只有一条正确路径，让模型选工具是增加不确定性；
> 二是金额和库存必须逐字正确，模板可以单测，模型输出不行。
> 代价是用户说『我上周买的那个推车』这种没有单号的话，只能列候选让他点。」

**代码**：`app/graph/data_exit.py`（子图）、`app/tools/orders.py`（工具层）

## 2. 流水线（5 状态 / 8 转移 / 3 个守卫）

```
extract_params ─► validate ─┬─► query ─┬─► format ─► END
                            │          ├─► need_info ─► END
                            └─► need_info       └─► 转人工（工具异常）
```

| 节点 | 一句话 |
|---|---|
| `extract_params` | 正则抽订单号 / SKU；规格不在这里抽 |
| `validate` | 按意图检查必填参数，写 `pending_question` |
| `query` | 调工具；物流走固定两级链；结果校验也在这里 |
| `need_info` | 缺什么列什么候选：订单 / 型号 / 规格 |
| `format` | 模板拼回答，数字只读 `data_result` |

**为什么没有 `judge` / `compute` / `compliance`**：B 出口只读，不涉及资金判定和合规红线。
这不是"简化"，是**职责边界**——把合规检查塞进只读查询，会让两个出口的失败语义混在一起。

**三个守卫**：

| 守卫 | 分支 |
|---|---|
| `after_validate` | 参数齐 → `query`；缺 → `need_info` |
| `after_query` | `ok` → `format`；`not_found` / `invalid_arg` → `need_info`；`timeout` / `internal` → 转人工 |
| `after_need_info` | 总是 `END` |

**为什么 `need_info` 无条件结束**：本轮只负责"把问题问出去"，
用户回答后是**下一次图执行**，从 `extract_params` 重新走。
跨轮恢复靠 DB 的 `pending_question`，与 C 出口一致；`interrupt` 要等 Ch05 的 checkpointer。

## 3. 三个关键设计

### 3.1 工具层统一错误语义

```python
@dataclass(frozen=True)
class ToolResult:
    ok: bool
    code: str | None      # not_found / invalid_arg / timeout / internal
    data: dict | None
```

**为什么不让图里 try/except**：图只做分支，异常处理集中在工具层，
每个错误码都能单测；否则每个节点都要写一遍 `except`，迟早漏。

**四个错误码按"用户能不能补"分流**：

| code | 含义 | 去向 |
|---|---|---|
| `not_found` | 查不到 / 不是本人的 | 追问（列候选） |
| `invalid_arg` | 参数缺失 | 追问 |
| `timeout` | 超时 | 转人工 |
| `internal` | 数据异常 | 转人工 |

### 3.2 结果校验放在 `query` 里，不放在守卫

守卫只能返回下一个节点的键，**写不了转人工话术**。
放在 `query` 里，缺字段时能同时写 `tool_code=internal` 和 `transfer_reason`。

**为什么不在 `format` 里兜底**：`format` 的职责是拼文案。
如果它还要判断"数据能不能用"，模板测试就得覆盖两条失败路径；
分开之后，进入 `format` 的 `data_result` 永远是完整的，
数据异常会被明确记成 `internal`，而不是拼出一句「None 元」。

### 3.3 模板只读数据，不做二次计算

| 意图 | 模板 |
|---|---|
| 订单 | `订单 {id}：状态 {status}；实付 {amount}；下单时间 {created}。` |
| 物流 | `快递 {no}：最新状态 {latest}。{最近 3 条轨迹}` |
| 库存 | `{sku} {spec}：{货态}，售价 {price}。` |

金额用 `yuan_text(cents)`（整数除法和取余），库存数量直接来自工具，
时间只做 ISO → `YYYY-MM-DD HH:MM` 的格式转换。

**可讲**：「这样能保证『回答里的数字 = 数据库里的数字』，
而且模板可以逐字单测——`deepseek` 输出一句话，测试没法逐字断言。」

## 4. 安全：越权与不存在必须同一条路径

| 层 | 做法 |
|---|---|
| 图 | `user_id` 由**图传入**，不是模型传入 |
| 仓库 | `get_order(order_id, user_id=...)` 在 SQL 层过滤 |
| 工具 | 不存在与越权都映射成同一个 `not_found` |
| 回答 | 同一句「没有找到这笔订单，您可以选一笔最近的订单：」 |

**为什么必须同一句**：如果"不存在"和"不是你的"回答不同，
攻击者可以拿订单号枚举——不同回答就是"这笔单存在"的信号。

**和 Ch03 的对比**：C 出口同样复用这套 `not_found` 语义，
所以"越权防枚举"在两个出口是同一份实现，不是各写一遍。

**代码**：`app/tools/orders.py`、`app/db/repo_order.py`、`app/graph/order_select.py`

## 5. 四个踩坑故事（STAR）

### 5.1 共享代码搬家后，测试静默失效

- **S**：Ch04 要把 C 出口的 `_ask_order` / `_candidate` / `extract_order_id` / `_traced` 抽成共享模块
- **T**：纯搬移，C 出口行为不能变
- **A**：函数搬到 `graph/order_select.py`、`graph/params.py`、`graph/tracing.py` 之后，
  测试里的 `monkeypatch.setattr(rules_exit, "list_user_orders", ...)` **不再生效**
- **R**：把所有 patch 目标改到新模块；C 出口的断言一条没改，全绿——这才证明搬移没改行为

**可讲**：「测试不会因为 patch 打错位置而报错——它会打到一个没人用的符号上，
然后测试照样过。所以重构后要专门检查 patch 目标。」

### 5.2 规格匹配取最长命中

- **S**：用户说「我要星光灰」，库存里有「灰」和「星光灰」两个规格
- **T**：子串匹配会先命中「灰」
- **A**：`max(hits, key=len)` 取最长；只有一个规格时用户不说也能确定；多规格且没命中 → 追问
- **R**：不会把「星光灰」错答成「灰」的价格和库存

**可讲**：「规格是开放集合，正则枚举不完，所以从数据库取该 SKU 的所有规格再匹配。
匹配不到就不猜——猜错的价格比追问更贵。」

### 5.3 待发货查物流不是错误

- **S**：用户问「订单 1003 到哪了」，这单还没发货，`tracking_no` 是 NULL
- **T**：如果按 `not_found` 处理，用户会以为订单丢了
- **A**：把"没有物流单号"当成**正常数据状态**：`data_result.tracking = None`，
  `format` 输出「订单 1003 当前状态：待发货，暂无物流信息。」
- **R**：不报错、不追问、不转人工

**可讲**：「NULL 不代表错误，它代表业务状态。把 NULL 一律当异常，
是数据查询出口最常见的误报来源。」

### 5.4 占位机制整体删除，而不是逐个删

- **S**：Ch02 时五个出口里除了 A 都是 `PLACEHOLDER_TEXT` 占位
- **T**：B 出口接上真实子图后，占位机制没有消费者了
- **A**：删掉 `nodes.py` 的 `data_exit` / `PLACEHOLDER_TEXT` / `_placeholder` 整组代码，
  并把冒烟测试里"所有出口都无数字"的断言改成**排除 data**
- **R**：仓库里不存在"看起来还没实现"的死代码；测试断言也符合新语义

**可讲**：「删占位时发现一条旧断言会误伤——数据回答本来就该有价格和单号。
这说明测试也在跟着架构演进，不是一次写死。」

## 6. 追问清单

| 问题 | 答题要点 |
|---|---|
| B 出口为什么不用模型？ | 参数结构化、答案是读数、答错代价高；只有一条正确路径 |
| 那为什么上游还调模型？ | 意图分类是自然语言，开放集合；进了 B 就零模型 |
| 怎么保证金额正确？ | 模板 + 数据库原值 + `yuan_text` 整数运算 + 逐字单测 |
| 缺订单号怎么办？ | 列最近 3 单 + `actions.type=select_order`，点选比打字可靠 |
| 用户说「第一单」呢？ | 不支持，属 Ch05 槽位填充；本章只认回传订单号 |
| 越权怎么防？ | `user_id` 图注入 + SQL 过滤；不存在与越权同 `not_found` |
| 工具超时怎么办？ | 转人工，fail-closed；不让模板拼半截数据 |
| 为什么物流是两级链？ | 先订单拿 `tracking_no`，再查轨迹；只有一条正确路径，固定写死 |
| 为什么不用 function calling / ReAct？ | 模型选工具增加不确定性；固定链可单测。ReAct 留给 E 出口长尾 |
| 规格为什么不用正则？ | 规格是开放集合；从库里取该 SKU 的所有规格再匹配更可靠 |
| 多规格没命中怎么办？ | 追问，不猜；`spec_candidates` + `select_spec` |
| 库存并发怎么办？ | 本章只读快照，不预留不下单；下单是后续章节 |
| 怎么测图结构？ | 5 节点 / 8 边 / 守卫键 / 可达性 / 空走终止，都是结构断言 |
| 怎么保证零模型？ | `test_data_exit_does_not_import_llm` 静态断言模块不依赖 `app.core.llm` |
| 为什么没有 gold set？ | 有唯一正确答案，单测逐字对拍即可；gold set 用于模型参与判定的出口 |
| 延迟多少？ | 中位 0.98s（n=5），只有上游分类一次模型调用 |
| 这个出口的瓶颈？ | 用户表达 → 参数的映射；商品名到 SKU 需要商品目录，当前数据没有 |

## 7. 不要说的话

| 别说 | 为什么 |
|---|---|
| 「B 出口用了 Agent」 | 明确不用；用了反而要解释为什么固定流程还上 Agent |
| 「模型生成回答」 | 是模板，数字必须逐字等于数据库 |
| 「支持多轮」 | 用户回传单号才能接上；「第一单」不支持 |
| 「库存实时准确」 | 查询时刻的快照，不预留不下单 |
| 「线上跑了」 | 从未部署 |
| 「准确率 100%」 | 没有评测集，只有单测对拍，不能这么说 |
