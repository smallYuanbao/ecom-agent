# Ch03 面试要点：退款规则出口

> 证据来源：[ch03-acceptance.md](../reports/ch03-acceptance.md)、[refund-eval.md](../reports/refund-eval.md)、[ch03-rules-exit-changes.md](../reports/ch03-rules-exit-changes.md)

## 0. 30 秒版本

> 「这个项目是电商售后客服 Agent，有五个出口：知识、数据、规则、转人工、兜底。
> 我做的是 **C 出口：退款**。它是一个 **9 状态的确定性流水线**：
> 受理 → 抽取 → 校验 → 查数 → 判定 → 算钱 → 合规核对 → 回复。
>
> **资格由模型判，金额由纯函数算，合规由规则代码独立复算。**
> 模型和代码结论不一致时转人工——不以代码为准，也不采信模型。
>
> 评测上我做了 30 条人工标注的分组 gold set：简单组 20 条不退化，
> 困难组模型 7/10、规则只有 2/10。这个差距就是"为什么值得用模型"的证据。」

## 1. 架构：为什么是 Workflow，不是 ReAct

**结论**：C 出口不接 ReAct。有明确规则、金额、合规要求的地方用确定性流程；长尾才上 Agent。

| 判据 | C 出口（退款） | 适合 Agent？ |
|---|---|---|
| 步骤是否固定 | 是（受理→判定→算钱→回复） | ❌ |
| 输出是否有唯一正确答案 | 是（能不能退、退多少） | ❌ |
| 错了的代价 | 退错钱 / 合规风险 | ❌ |
| 需要探索、多步工具 | 否 | ❌ |

**可讲的取舍**：

> 「参考实现（MewHelp）在退款上也是先 `retrieve_policy` 再交给 Agent，
> 但它的判定最终仍由模型自由完成。我把它拆成了**判定节点 + 合规复算节点**：
> 模型负责理解用户和政策，代码负责兜底。这是 Workflow 和 Agent 的分工，
> 不是二选一。」

**代码**：`app/graph/rules_exit.py`、`app/rules/eligibility.py`

---

## 2. 核心设计：模型判定 + 代码复算

**三种方案与取舍**：

| 方案 | 做法 | 问题 |
|---|---|---|
| 全代码 | 规则表写死所有情形 | 规则表永远不全，长尾只能转人工 |
| 全模型 | 模型读完政策直接给结论 | 不可审计，判错无法拦截 |
| **混合（本方案）** | 模型判 → 规则代码复算 → 不一致转人工 | 覆盖会下降（见 §4） |

**为什么分歧时不以代码为准**：
- 以代码为准 → 模型白用了，等于回到纯规则；
- 直接采信模型 → 失去可审计性；
- **转人工是第三条路**：代价是体验，换来"分歧必被看见"。

**代码**：`compliance` 节点；`_divergence()` 比的是 `(eligible, reason_code)` 一整对，
不是只比"能不能退"。`ok` 和 `reject_then_refund` 都算可退，但一个让用户寄回、一个让用户拒收。

**已经踩到的代价**：困难组里 H06 / H10 模型判对、规则判错，
`compliance` 把正确答案升级成了转人工，流水线覆盖从 7/10 掉到 5/10。
**这不是模型的问题，是规则表的问题。**

## 3. 流水线（9 状态）

```
intake ─► extract ─► validate ─► query_data ─► judge ─► compute ─► compliance ─► respond
  │                     │  ▲           │  ▲        │
  │                     │  └ need_info ┘  │        │
  │                     └──(2 次失败)─────┼────────┼──► 转人工
  └──(缺订单号)──► need_info              └────────┘
```

| 节点 | 一句话 |
|---|---|
| `intake` | 正则抽订单号；抽不到进追问 |
| `extract` | 模型抽原因 / 件数 / 完好 / 是否拆封 |
| `validate` | 要素齐不齐、是不是本人的单、日期是否矛盾 |
| `need_info` | 缺什么问什么；缺单号列最近 3 单 |
| `query_data` | 订单快照（复用 validate 的）+ 政策检索 top5 |
| `judge` | 模型判资格，给理由码 + 置信度 |
| `compute` | 纯函数算金额（分） |
| `compliance` | 四条红线 + 规则代码复算 |
| `respond` | 组织话术，金额只复述 |

**「转人工」不是第 10 个节点**：主图已有 `human` 出口，子图把转人工写成一条边到 `END`。

### 三道 fail-closed 闸

| 闸 | 条件 | 行为 |
|---|---|---|
| `extract` | `condition_ok` 为 null | 不判"不完好"，交给下游 |
| `judge` | `confidence < 0.7` | 转人工 |
| `compliance` | 模型与代码分歧 | 转人工 |

## 4. 评测：这一章最值钱的部分

### 4.1 两组 gold set

| 组 | 条数 | 测什么 |
|---|---|---|
| 简单组 | 20 | 规则覆盖范围内，模型**有没有退化** |
| 困难组 | 10 | 规则判不了 / 判错，模型**有没有增量价值** |

**为什么必须分组**：规则实现在简单组 20/20 全对。
只报总准确率，模型最好也只是"打平规则"，看不出它存在的理由。

### 4.2 三列指标

| 列 | 含义 | 用途 |
|---|---|---|
| 模型 | `judge` 原始判定 | **验收对象** |
| 规则 | `judge_eligibility` 结论 | 基线 |
| 流水线 | 模型 + `compliance` 之后 | 诊断：用户实际看到什么 |

**为什么验收卡模型**：流水线同时受规则质量影响。混在一起会分不清"规则错了"还是"模型错了"。

### 4.3 实测结果

| 组 | 模型 | 规则 | 流水线 |
|---|---|---|---|
| 简单组 20 | **20/20** | 20/20 | 20/20 |
| 困难组 10 | **7/10** | 2/10 | 5/10 |
| 金额 10 份 | — | — | **10/10** |

- 错放率 0%（0/9）、错拦率 0%（0/10）
- 端到端 P95 **4.72s**（n=5，预算 30s）
- 单轮 4 次模型调用：分类 / 抽取 / 判定 / 回复

### 4.4 未命中怎么归因（比总分更重要）

困难组 5 条未命中：

| 根因 | 条数 | 案例 |
|---|---|---|
| prompt | 1 | H03（签收时间为空没被当数据缺口） |
| 规则表 | 2 | H06（顺序）、H10（字段粒度） |
| 数据模型 | 2 | H05（无承诺字段）、H08（完好程度是订单级） |

**结论**：瓶颈不只在模型，还在规则表和数据字段能不能表达业务。

### 4.5 样本量的诚实边界

`7/10` 的 95% Wilson 区间约 **[40%, 89%]**。

> 「这个样本量只能支撑方向性结论——模型显著优于规则（7 vs 2），
> 支撑不了'准确率 70%'这种精确表述。扩充计划在 Ch07：
> 分层抽样、留盲测、报置信区间。」

**加分点**：主动说出这一点，比硬报 70% 更让人信任。

### 4.6 dev/test 污染

这 10 条已经用来改过两次 prompt（`condition_ok=null` 禁令、原话优先），
**它事实上是 dev set**。所以新增评测集必须留一批不参与调参的盲测题。

## 5. 四个踩坑故事（STAR）

### 5.1 规则 8 的顺序缺陷（集成测试发现）

- **S**：整条子图真跑 `订单1004 辅食机有异响，我试了一次`
- **T**：模型判"可退"，规则判"不完好"，`compliance` 触发分歧
- **A**：查到规则 8 把"用过"一律判成不完好；但异响不开机发现不了，
  "试了一次"是验证缺陷，不是把商品用旧了。改为：质量问题 + `condition_ok=false` → 代码返回 `None`（不否决模型）
- **R**：同一单正常放行；规则单测新增一条正例

**可讲**：「单元测试发现不了这个——它只在整条链路拼起来后才暴露。」

### 5.2 金额被追加了两次（端到端发现）

- **S**：`respond` 要求回答里必须出现金额，否则机械追加
- **T**：模型写「1249.00元」（少一个空格），严格匹配没认出来，金额出现两次
- **A**：比较时忽略空格、千分位逗号、全角空格，只要求数字和小数位一致
- **R**：金额只出现一次

**可讲**：「给模型的是金额字符串，不是数字——给数字它会自己除以 100，单位一错就是资金问题。」

### 5.3 prompt 改了两轮（真模型测出来的）

| 问题 | 改法 |
|---|---|
| 「试了一次」被整句忽略 | 明确：不是件数，但说明被用过 → `condition_ok=false` |
| 「不太确定算不算用过」被判成 `false` | **用户在陈述事实就判断，在表达犹豫就留空** |
| H10「只拆快递盒、塑封没动」被判成已拆封 | **抽取字段与原话矛盾时，以原话为准** |

**可讲**：「只看 mock 这两处永远发现不了。」

### 5.4 评测口径错误（自己抓出来的）

第一版评测把规则返回 `None` 映射成"转人工"后直接和模型比，
导致"代码判不了"被误算成分歧，流水线分数被低估。

**改法**：`rule_none` 单独标记；代码判不了时**不否决**模型。

**可讲**：「评测代码本身也会错，所以要先验证评测语义和线上一致。」

## 6. 追问清单

| 问题 | 答题要点 |
|---|---|
| 为什么不直接 if-else？ | 困难组规则 2/10；规则表永远不全 |
| 为什么用模型判？ | 政策是自然语言；规则表覆盖不了长尾；有 compliance 兜底 |
| 模型判错了怎么办？ | 低置信度转人工 + 规则复算 + 红线 |
| 分歧为什么不以代码为准？ | 模型白用；采信模型失去审计；转人工是第三条路 |
| 金额怎么保证？ | 纯函数（无 IO / 无时钟 / 无随机）+ 10 份手算合同对拍 |
| 怎么测 LLM 系统？ | 代码部分单测；模型部分 gold set；真模型测试允许省略、禁止猜错 |
| 什么是不确定性最大的地方？ | 模型判定；用 temperature=0 + 多次运行 + 分组评测控制 |
| 为什么 `condition_ok` 是三态？ | 用户没说清时逼模型二选一，会变成瞎猜 |
| 为什么日期倒挂直接转人工？ | 用户改不了 ERP / 时区造成的矛盾，追问浪费一轮 |
| 为什么缺单号列候选？ | 用户记不住订单号；点选比打字可靠，顺带完成归属校验 |
| 越权怎么防？ | `user_id` 必填 + SQL 层过滤；不存在与越权同异常，防枚举 |
| 跨轮怎么恢复？ | 当前靠 DB 的 `pending_question` + 下一轮重新抽单号；`interrupt` 在 P5-12 |
| 为什么不用 `interrupt`？ | 需要 checkpointer，且会丢弃节点返回值；Ch05 再做 |
| 怎么观测？ | 每个节点一行 `trace_span`；子图 `rules:<node>` |
| 7/10 说明什么？ | 方向性结论；CI [40%, 89%]；扩充在 Ch07 |
| 如果政策变了？ | 改 `data/kb` + `kb_version` 哈希；评测重跑 |
| 这个项目的瓶颈在哪？ | 规则表表达力 + 数据字段粒度，不是模型 |
