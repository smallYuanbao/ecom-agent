## 1. 架构：多轮底座 + E 出口 ReAct

```
/api/chat
  ├─ 会话锁（5s）
  ├─ 读会话 + 读三个流程字段
  ├─ 槽位填充（命中 → resume_route）
  ├─ 读历史窗口（不含本轮）
  ├─ 主图：resolve_reference → classify_intent → 五个出口
  │      └─ E：gate → agent（只读 ReAct） | scripted
  └─ 写助手消息 + 流程状态（同一事务）
```

**主图形状不变**：五个出口的节点名与边都没动，多轮逻辑在入口和出口内部完成。
`fallback` 从普通节点换成子图，顶层仍是 `fallback`。

## 2. 为什么不引入 checkpointer

**结论**：当前用「新 turn + 槽位填充 + `classify_intent` 短路」，不引入 checkpointer。

| 方案 | 恢复粒度 | 代价 |
|---|---|---|
| **DB 三字段（本方案）** | 下一轮从入口重跑，靠 draft 接上 | 每轮多一次抽取调用 |
| checkpointer + `interrupt` | 同一轮从断点续跑 | thread 生命周期、节点幂等、状态清理 |

**为什么当前不需要**：

- 主路径是确定性流水线，每轮本来就要重新判定/回复；
- 追问只有 1–2 个槽位，draft 足够恢复；
- 没有「人工审核必须插在流程中间」的需求。

**这个方案的缺点（要主动说）**：

- 状态是有损投影：只存三个字段，新增字段要手动同步；
- 每轮重跑：纯补订单号已用 `skip_extract` 省掉抽取；
- 槽位填充只认固定形状：「第一单」「那个推车」不行；
- 路由多了一个入口：`resume_route` 短路。

**什么时候上 P5-12**：

- 同一轮内必须原地续跑；
- 人工审核要插在流程中间；
- 长流程重跑成本明显。

**代码**：`app/core/session_state.py`、`app/api/chat.py`、`classify_intent`

## 3. 跨轮状态：三个字段 + draft

`conversations` 只存三个字段：

```json
{
  "active_flow": "refund",
  "pending_question": "order_id",
  "draft": {
    "intent": "退款申请",
    "order_id": "1002",
    "validate_retry": 0,
    "refund": {"reason_code": "no_reason"}
  }
}
```

| 字段 | 回答的问题 |
|---|---|
| `active_flow` | 当前在跑哪个流程 |
| `pending_question` | 还缺哪个槽 |
| `draft` | 已经知道了什么 |

**draft 为什么嵌套**：外层是流程元信息，内层 `refund` 直接塞回 `state["refund_draft"]`，
不会把 `intent` / `validate_retry` 混进判定 prompt。

**30 分钟失效**：

- 读时惰性判断，超过 TTL 就清空；
- `scripts/cleanup.py` 批量清理；
- 按「最后活动时间」，不是「park 时间」——长对话可能让旧流程不过期，已知限制。

**同一会话只保留一个 `active_flow`**：新流程替换旧流程，trace 记 `flow_replaced`。
两个流程抢同一个 `pending_question` 会把用户回答喂错。

**代码**：`app/db/models.py`、`app/core/session_state.py`、`scripts/cleanup.py`

## 4. 上下文窗口与摘要

**预算按块分配**，不用全局 70%：

```
8000 自设上限
 ├─ 系统提示 + 工具  1200
 ├─ 检索证据        2000
 ├─ 摘要段           600
 ├─ 输出预留         800
 └─ 历史窗口        3400
```

**几个关键决定**：

| 决定 | 原因 |
|---|---|
| 中文按 **1 字符 ≈ 1 token** | 按 4 字符/token 会低估约 4 倍 |
| 窗口**不含本轮用户消息** | 本轮由 `raw_query` 单独传，避免重复 |
| 至少保留最近 2 轮原文 | 不把当前上下文裁没 |
| 摘要边界**只向前移** | 并发/重试时旧任务不能把边界拉回去 |
| 摘要失败保留旧摘要 | 3s 超时；不阻断本轮 |
| 工具消息超 200 字压成一行 | 一次订单 JSON 就能吃光窗口 |

**摘要触发**：未压缩历史超过预算 → 最老一半压成摘要。
边界一次挪到位，保护 prompt cache。

**代码**：`app/core/history.py`

## 5. 指代消解 + 槽位填充

### 指代消解

三个零成本短路（不调模型）：

1. 历史为空；
2. 原句已含订单号 / SKU；
3. resume 轮（「1002」是在补槽位，不是问句）。

**Prompt 三条关键规则**：

- 指代订单时必须带订单号，不能只补商品名（同一商品可能有多单）；
- 通用政策问题不要硬塞订单号/商品名（绑上后检索反而查不到）；
- 口语/情绪归一成标准问法，保留关键实体。

**结果守卫**：

- 空 / 少于 2 字 → 原句；
- 超过 `max(2×原长, 原长+24)` → 原句（防扩写）；
- 只差空白 → 原句；
- 5s 超时 / 格式错误 → 原句 + `passthrough_error`。

**摘要行也进 coref 上下文**：跨滑窗的「最开始那个订单」只能靠摘要兜住。

**代码**：`app/core/coref.py`、`app/core/prompts.py`、`nodes.resolve_reference`

### 槽位填充

```
没有 pending_question → 直接返回
取消词 → 恢复词 → 结构化点选 → 按槽位抽取 → 没命中
```

| 槽位 | 方式 |
|---|---|
| `order_id` | 全角数字归一 + 正则 |
| `sku_id` | 正则 + 转大写 |
| `spec` | 透传，匹配交给数据出口 |
| `reason_code` | 复用 C 出口抽取器，合并而非覆盖 |

**为什么不把「补充信息」做成意图**：`1002` 在别的场景可能是订单查询；
塞进意图分类会污染意图体系。

**代码**：`app/core/slot_fill.py`

## 6. park 与会话锁

### park

| 本轮终态 | 对旧流程 |
|---|---|
| 新流程又要求补参 | 存新流程（替换旧的） |
| 旧流程还在、本轮没接回、不是转人工 | **保留旧流程** + 提示 + `resume_flow` |
| 本轮接回并完成 / 取消 / 转人工 | 清空 |

提示只加一次：

```
（您还有一笔未完成的退款申请，需要继续吗？）
```

**决策与落库分开**：`decide_flow` 是纯函数，先拼回答再写库；
写库仍与助手消息同一事务。

**代码**：`session_state.decide_flow` / `apply_flow_decision`、`chat.py`

### 会话锁

- 粒度 `conversation_id`，同会话串行，不同会话并行；
- 等待上限 **5s**，超时返回 `busy`；
- **先拿锁、再读会话**：否则两个并发会各自读到上一轮还没写库的旧状态；
- 单进程有效，多实例要 Redis / DB 锁。

**5s 怎么定**：C 出口 P95 约 4.72s，5s 刚好覆盖大多数正常轮次；
再长用户会以为卡死。

**代码**：`app/core/lock.py`

## 7. 只读 ReAct（E 出口）

**为什么只放在 E**：

| 出口 | 为什么不接 |
|---|---|
| A 知识 | 无工具选择空间 |
| B 数据 | 固定链，数字必须逐字正确 |
| C 规则 | 涉及资金与合规，必须可复算 |
| D 转人工 | 无决策空间 |
| **E 兜底** | 唯一开放域；只读，错了也不会动钱 |

**gate 判断值不值得上**：订单号 / SKU / 数据关键词才进 ReAct；
「你好」「谢谢」直接走脚本，不产生模型调用。

**四个工具**：

| 工具 | 参数 | 实现 |
|---|---|---|
| `query_order` | `order_id` | 查订单 |
| `query_logistics` | `order_id` | 内部先取 tracking_no，再查轨迹 |
| `query_stock` | `sku_id`, `spec?` | 查库存/价格 |
| `search_kb` | `query`, `top_k?` | 检索政策 |

**三条硬约束**：

1. **只读**：白名单写死；写工具连 schema 都不给模型看；
2. **身份注入**：schema 里没有 `user_id`，模型传了也丢弃；
3. **never-raises**：工具异常/超时转 `{"code": ...}` 回灌，不中断循环。

**4 步封顶**：最后一步不带工具，强制基于已有结果回答。
`code=ok / step_limit / error`。

**结果截断**：单条工具结果 ≤2000 字；原文进 trace，模型只拿头部。

**金额/价格**：只回灌 `amount_text` / `price_text`，不把「分」直接给模型。

**代码**：`app/core/react.py`、`app/graph/fallback_agent.py`

## 8. 三个踩坑故事（STAR）

### 8.1 第一轮的原因丢了

- **S**：用户说「我要退款，尺寸不合适」，没给订单号；
- **T**：C 出口缺订单号时直接 `need_info`，**跳过了 `extract`**；
- **A**：轮末 `_capture_refund_draft`：问订单号且 draft 缺原因时，补一次抽取；
- **R**：第二轮补单号后直接判定，不再问原因。

**可讲**：「这是验收跑真模型才发现的——单测里每个节点都喂好了状态，看不出这个顺序问题。」

### 8.2 `validate_retry` 把「继续」也当失败

- **S**：退款挂起 → 问订单号 → park → 「继续退费」→ 补单号；
- **T**：每次追问都 `+1`，三次后直接转人工；
- **A**：槽位命中 / 恢复轮把 `validate_retry` 重置为 0；
- **R**：问订单号、问原因、回答，正常完成。

**可讲**：「计数器要数‘失败’，不是数‘问了几次’。park 和 resume 不是失败。」

### 8.3 ReAct 把 129900 分当成元

- **S**：ReAct 同时查物流和库存；
- **T**：工具返回 `price: 129900`（分），模型回答「129,900」；
- **A**：回灌前转成 `price_text: 1299.00 元`，移除原始分值；
- **R**：回答正确。

**可讲**：「给模型的数字必须带单位；给分它就会当成元。」

## 9. 追问清单

| 问题 | 答题要点 |
|---|---|
| 为什么不用 checkpointer？ | DB 三字段足够；重跑成本低；需要同轮续跑/审批时再上 P5-12 |
| 新 turn 方案缺点？ | 有损投影、重跑、槽位只认固定形状、两条路由入口 |
| `pending_question` 和 `draft` 区别？ | 还缺什么 vs 已经知道什么 |
| 为什么窗口不含本轮消息？ | 本轮由 `raw_query` 传，避免重复 |
| 摘要边界为什么只前移？ | 并发/重试不能把已压掉的消息放回窗口 |
| 为什么不用全局 70% 预算？ | 加证据/提示时会悄悄把历史挤没 |
| 指代消解为什么要每轮做？ | 意图是阀门，阀门错了后面全错 |
| 三个短路是什么？ | 无历史、含实体、resume 轮 |
| 槽位填充为什么先判 `pending_question`？ | 没有待补槽位就不该产生 cancel/resume 信号 |
| 为什么不把补充信息做成意图？ | 会污染意图体系（「1002」在别处是订单查询） |
| park 与「新流程也要追问」冲突？ | 单 `active_flow`，新流程替换旧流程并记 trace |
| 锁为什么 5s？ | 覆盖 C 出口 P95 ~4.7s；再长用户以为卡死 |
| 锁能防多实例吗？ | 不能，进程内锁；多实例要 Redis/DB 锁 |
| ReAct 为什么只在 E？ | A 无选择、B 固定链、C 资金、D 无决策；E 是开放域 |
| 为什么只读？ | 写操作要确认+幂等+审计，不能让模型自由选 |
| 4 步怎么定？ | 查询 + 补查 + 回答；一步一次模型调用，可数 |
| 怎么防模型编造？ | 只读工具 + 结果回灌 + 提示词要求查不到就说 + 脚本兜底 |
| ReAct 有评测吗？ | 没有 gold set，只有场景/单测；Ch07 补 |
| 多意图怎么办？ | 当前不处理（P5-11）；一句话只答主诉求 |
| 如果继续做什么？ | 多意图、ReAct 评测、token 流式、多实例锁 |
