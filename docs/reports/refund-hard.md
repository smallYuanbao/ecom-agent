## 按组归因

- **规则顺序**（模型 3/3、规则 3/3、流水线 3/3）：参照组：gold 与规则表一致（状态规则 1–5 优先于类别规则）。它测的是模型是否遵循既定优先级，不承担「规则失败」的难度指标。
- **字段粒度**（模型 3/3、规则 0/3、流水线 1/3）：request 是订单级字段。模型多数能按「要退的那件」判对，但规则会用整单的 `condition_ok` / `packaging_opened` 否决；要释放覆盖，得拆到件级，或让 compliance 按件判断。
- **数据缺口**（模型 3/3、规则 2/3、流水线 3/3）：缺 `signed_at` / `category` 时应转人工；若模型仍补默认结论（超期/可退），这是优先修复项。
- **语义模糊**（模型 3/3、规则 0/3、流水线 3/3）：只拆外箱、剪吊牌、用过一次这类描述，是 condition 语义理解的主要检验点。
- **多轮补充**（模型 3/3、规则 1/3、流水线 3/3）：槽位已解析时判定正常；换货/维修等非退款诉求仍是风险点。

## 结论与边界

- held-out test 模型 **15/15**，95% CI **80%–100%**；其中规则顺序参照组 3/3（gold 运行后修正），其余 4 组 12/12。不能当作严格盲测准确率。
- prompt 修改后 dev 三次为 9/10、10/10、10/10；gold 修正后 test 三次均为 15/15。
- 单次 run；同批 test 重跑仍可能有波动（temperature=0 也不保证逐字一致），本表是其中一次，结论要结合多次运行看。
- dev 组已参与调参，不能当作盲测；两者分开报，不合并平均值。
- dev 组 10/10，仍满足 Ch03 的 7/10 门槛。
- 金额合同是确定性检查，不受 judge 方差影响。
- 「多轮补充」类只测已解析槽位下的判定，不等价于完整多轮链路（后者在 Ch05）。

## held-out 纪律

- test 案例在第一次运行前已定稿；prompt 修改只依据 dev 的失败，没有按 T01–T15 的个案调规则。
- 但运行后发现 T01/T03 的 gold 与主评测 B07 / 规则表冲突，已按规则表修正；规则顺序组因此降为参照组。
- 加上修改前已经看过一次 test 结果，这组只能称为 **held-out 验证**，不是严格意义的盲测。
- 若后续再改 prompt 或 gold，必须使用新一批没看过的样本。
