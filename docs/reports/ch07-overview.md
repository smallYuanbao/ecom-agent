## 一、Ch07 到底在干什么

Ch01–Ch06 把功能做出来了：能查订单、能算退款、能多轮、能防注入。
但有一个问题没有答案：**它到底好不好？改了一行 prompt，是变好还是变坏？**

Ch07 不新增用户功能，它做的是**给系统装一套体检设备**：

| 体检类比 | Ch07 里的东西 |
|---|---|
| 体检项目固定 | 44 条评测集、退款困难组 |
| 抽血窗口 | `/api/eval/chat` |
| 血压/身高（客观、不抖） | `eval_e2e.py` 确定性检查 |
| 医生主观评分（有抖动） | EvalFlow 的 judge 指标 |
| 重复测量 | judge 方差校验 |
| 参考范围 | 证据闸阈值曲线 |
| 体检报告 | run-01 / run-02 / run-03 / acceptance |

一句话：**Ch07 把“感觉还行”变成“有样本、有指标、有置信区间、有已知边界”。**

### 它不是什么

- 不是新业务功能；生产 `/api/chat` 的行为没有因为它改变；
- 不是“刷分”；很多结论恰恰是“这个提升是噪声，不能算”；
- 不是一次性报告；它留下了可重复执行的脚本和基线，后面每章都能用。

## 四、十个任务：为什么做、做了什么、结果是什么

### Task 1 · 44 条评测集

**为什么**：没有固定样本，所有“变好了”都是主观感觉。

**做了什么**：

- `data/eval/eval_v1.yaml`：44 条，7 个桶；
- 每条带 gold：期望路由、退款资格/金额、动作、回答要点、检索 id；
- 标 `dev/test`；被污染过的旧题移到 `eval_v1_dev_archive.yaml`；
- 题目来源：385 条外部模型候选 → 58 条 shortlist → 人工审核成 44 条。

| 桶 | 条数 | 测什么 |
|---|---|---|
| B1 知识 | 10 | 政策/商品问答、检索与引用 |
| B2 数据 | 8 | 订单、物流、库存、价格 |
| B3 规则 | 8 | 退款 9 状态流水线 |
| B4 边界 | 6 | 定制、拆封、超期、部分退 |
| B5 异常 | 4 | 查不到、缺信息、异常输入 |
| B6 对抗 | 4 | 注入、越权、混合意图 |
| B7 转人工 | 4 | 投诉、赔偿、情绪升级 |

**结果**：有了可复现的“尺子”。

**记住**：评测集的质量决定后面所有结论的质量。

---

### Task 2 · 评测门面 `/api/eval/chat`

**为什么**：EvalFlow 要的是普通 JSON 请求-响应；生产 `/api/chat` 是 SSE 流式。
直接让平台适配 SSE，成本高，还容易把评测逻辑和生产逻辑混在一起。

**做了什么**：

- 新增非流式 `POST /api/eval/chat`；
- 返回 `answer / references / hits / route / signals`；
- `ENABLE_EVAL_API` 默认关闭，关闭时 404；
- 错误映射 422 / 504 / 404 / 429 / 500。

**结果**：生产 SSE 一点没动，评测平台有了稳定的入口。

**记住**：这是一个“只为评测存在”的门面，不是产品功能。

---

### Task 3 · 确定性跑分脚本

**为什么**：judge 有方差，但路由、金额、动作这些是硬约束，必须用不抖的检查。

**做了什么**：

- `scripts/eval_e2e.py` 调 `/api/eval/chat`；
- 只判：路由、字段、退款资格/金额、动作、回答必须包含的片段、检索 id、是否泄露系统提示；
- 不调 judge，所以同一代码重跑结果稳定；
- 产出 `run-local-01` … `run-local-06`。

**结果**：最终 `run-local-06` **44/44**。

**记住**：这是开发时的“快回路”，每次改代码先跑它。

---

### Task 4 · EvalFlow 适配器

**为什么**：确定性脚本只能看硬约束，回答质量（相关性、正确性、忠实度）需要 judge。

**做了什么**：

- `evalflow/backend/external_ecom.py`：
  - `EVAL_TARGET=ecom`；
  - 自我限流；
  - 429 / 5xx / 超时重试，4xx 不重试；
  - `hits` 映射成上下文。
- run 发起时写快照：模型、prompt 版本、KB 版本、数据集哈希。

**结果**：ecom 可以作为外部被测系统跑完整 44 条。

**记住**：慢回路，阶段性地看质量，不追求每次提交都跑。

---

### Task 5 · 指标语义修正

**为什么**：能跑不等于算得对。

**做了什么**：

- B2–B7 没有检索证据，不再给 recall / hit@k / MRR / context 写 NULL 行；
- `expected_output` 支持 `|` 任选，judge 能正确理解“A 或 B”；
- 修了 EvalFlow 在无 API key 时导入失败导致 CI 挂掉的问题。

**结果**：Task 5 本身**不跑报告**，它改的是后续 run 的写法。

- run-01（#31）仍显示 `10/44`，因为“不写行”的修正发生在 #31 之后；
- 从 run-02（#32）起才变成 `10/10`。

**记住**：覆盖率也是指标的一部分，“不适用的样本”不能混进分母。
这也是为什么 Task 5 和 Task 6 在时间上看起来“拧着”——计划是逻辑顺序，实际是联调时边跑边修。

---

### Task 6 · run-01 基线

**为什么**：先量一遍，才知道该修什么。

**做了什么**：

1. 44 条导入 EvalFlow；
2. 先跑 **#29**，暴露两个指标口径问题；
3. 修完后以 **#31** 作为 run-01 基线；
4. “无证据不写行”的修正发生在 #31 之后，所以 run-01 仍是旧覆盖率口径。

**结果**：

- recall 0.95 / context_recall 0.90；
- answer_correctness 0.9818；
- answer_relevance 0.8614；
- B1 `退货政策是什么` correctness **0.3**：没提“签收次日起 7 个自然日”；
- B5–B7 relevance 低：转人工/拒答被通用 judge 判成“不相关”；
- 覆盖率显示 `10/44`（旧口径），run-02 起修正为 `10/10`。

**记住**：run-01 的价值不是分数，而是**失败归因**。
另外，run-01 的覆盖率是历史快照，不需要为了口径统一去重跑——均值本来就不受 NULL 影响。

### Task 7 · 修复 + run-02 + 方差校验

**为什么**：run-01 暴露了失败，但不能“看到哪题低就改哪题”。
这一步要做四件事：**定修复边界、补知识层、修边界闸、确认变化不是噪声。**

#### 7.1 先定修复边界

- 只修 run-01 有归因的根因：B1 宽泛问法召回、边界样本误放/误杀；
- B1 的 10 条全部是 `split=dev`，28 条 test 不参与调参；
- 不在单题上打补丁，改的是通用机制（语料 / 闸 / prompt）。

#### 7.2 FAQ 知识层

**问题**：`退货政策是什么` 的 top-5 只命中“不适用商品”，
`returns#七日无理由退货的适用范围` 排第 8——宽泛问法没有对应入口。

**做法**：

- 新增 `data/kb/faq.md`：15 条 FAQ（退货 4 / 运费物流 6 / 优惠券 5）；
- 用“用户问法”做标题，标题参与 embedding + BM25；
- 重建 Chroma：chunk **42 → 57**，`kb_version=80bd26573951`；
  （Ch02 初始是 41；后来 `returns.md` 补了「已发货未收到」一节变成 42，
  再加 15 条 FAQ 到 57。文档里旧写法“41→57”把中间那次补漏掉了。）
- 同步更新 `expect_ids` 和要点正则（“可以登机 / 定做 / 你承担”等说法）。

**结果**：

| 指标 | 改前 | 改后 |
|---|---|---|
| dense hit@3 / MRR | 1.00 / 0.948 | 1.00 / **0.964** |
| bm25 hit@3 | 0.76 | **0.81** |
| hybrid hit@3 | 0.95 | **1.00** |
| 知识要点全覆盖 | 39/40 | **40/40** |
| 闸放行率 | 42/42 | 42/42 |

**代价**：FAQ 与 returns/member 有语义重叠，top-5 出现同事实两份表述，
后面 context_precision 从 0.91 降到 0.87。

#### 7.3 语义证据闸

**问题**：机械闸只有一个 top1 阈值，分不开：

```
能分期付款吗    0.572 → member#积分规则（话题近，没有答案）
FB-30 保修多久  0.566 → products#辅食机 FB-30（确实有答案）
```

**设计**：

```
top1 < 0.55          → weak（不调模型）
top1 >= 0.60         → strong（不调模型）
0.55 <= top1 < 0.60  → 边界带：调一次证据自评
                        sufficient=true  → strong
                        false/超时/异常 → weak（fail-closed）
```

- 自评超时 **3s**、**不重试**；
- 新增 `gate.py` 三态、`evidence_judge.py`、judge prompt、`judge_evidence` 节点、
  state 字段和配置；
- 只影响边界样本，C/E 路径不变。

**结果**：

| 类型 | 机械闸 | 语义闸后 |
|---|---|---|
| 可答题 42 | 42 放行 | **42 放行** |
| 该拒答 3 | 3 拦住 | 3 拦住 |
| 域外 8 | 7 拦住 | **8 拦住** |

边界 4 条全部判对；单次自评约 1.1s。

#### 7.4 run-02

- run **#32**，数据集哈希与 run-01 相同；
- 知识库换成新 FAQ，语义闸开启；
- 指标变化：

| 指标 | run-01 | run-02 |
|---|---|---|
| recall | 0.95 | **1.00** |
| context_recall | 0.90 | **1.00** |
| context_precision | 0.91 | 0.87 |
| answer_correctness | 0.9818 | **0.9977** |
| answer_relevance | 0.8614 | 0.9045 |
| 确定性通过 | 44/44 | 44/44 |

- `退货政策是什么` correctness **0.3 → 1.0**，B1 桶 0.92 → 0.99；
- 覆盖率从 `10/44` 修正为 `10/10`；
- 确定性回归过程中还修了 T04：其他用户的订单只列候选、不转人工
  （`need_info` 没传 `not_found`），并补了测试。

**明确不修**：`退货运费由谁承担` 的 0.9（要点语法）、B5–B7 的 relevance
（安全兜底）、ST-20 的 context_precision（产品块本身宽）——都记录为已接受项。

#### 7.5 方差校验

run-02 里出现“同一回答 judge 一次 0.0、一次 0.9”，所以同批 44 条又跑了
**#33 / #34**：

| 指标 | 三轮均值 | 标准差 | 极差 |
|---|---|---|---|
| answer_correctness | 0.9977 | 0.0023 | 0.45pp |
| answer_relevance | 0.8867 | 0.0195 | **3.86pp** |
| context_precision | 0.885 | 0.0132 | 2.5pp |
| recall / context_recall / faithfulness | 1.000 | 0 | 0 |

- 44 条回答只有 20 条三次完全一致（temperature=0.2），但 correctness 几乎不受影响；
- relevance 的抖动集中在 B5–B7 兜底话术：4 条**同回答**被判出 0.3–0.9；
- 结论：correctness / recall 的提升可信；relevance 的 +0.0431 在噪声带内，
  **不能归因于 FAQ**；context_precision 的 −0.04 也不能下结论。

#### 7.6 这一步真正的产出

| 类别 | 产出 |
|---|---|
| 产品 | FAQ 知识层、语义证据闸 |
| 口径 | 无证据不写行、要点 `\|` 任选 |
| 测量 | 3 次重复的方差报告，明确哪些 Δ 可信 |
| 决策 | 语义闸保留；Task 8 的阈值只依据确定性指标 |

**记住**：Task 7 不是“改一个 bug”，而是**修产品 + 校准测量**。
它也是 Ch07 里工作量最大的一步。

### Task 8 · 阈值曲线 + 质量传导 + 检索复核

**为什么**：回答三个参数/方法问题。

**做了什么**：

1. 证据闸 0.40–0.75、步长 0.01，机械 + 语义双列；
2. 质量传导 2×2：检索命中 × 答案覆盖要点；
3. 检索选型复核：35 条稀有词查询（型号/法条号/地区/发票），对比 dense / bm25 / hybrid。

**结果**：

- 机械闸做不到双零：0.53–0.56 可答全放行，但漏「能分期付款吗」，误放 9.1%；
- 语义闸把双零区间扩到 **0.53–0.56**，0.55 在中间，**维持 0.55**；
- 质量传导：自然 hit@3 42/42；错误证据 10 条 **0 编造**，人工核验 4 条均有依据；
- 检索：dense 1.00 / hybrid 1.00 / bm25 0.97，**维持 dense**，关闭 Ch02 待办。

**记住**：参数不是拍脑袋，是曲线和对照实验的结果。

### Task 9 · 退款困难组 + 评测方法论

**为什么**：退款是最容易出错的 C 出口，10 条样本不够，也没有置信区间。

**做了什么**：

- 旧 10 条转 dev；
- 新增 15 条 held-out，5 类 × 3：规则顺序 / 字段粒度 / 数据缺口 / 语义模糊 / 多轮补充；
- 加 Wilson 95% CI、per-class；
- 发现 `run_judge` 没把 case 的 `now` 传给 judge，模型用真实时间算 7 天窗口；
- 只依据 dev 修 judge prompt：数据缺口转人工、状态优先于类别、按件判定、非退款诉求。

**结果**：

- dev 5/10 → **10/10**；
- held-out 10/15 → **15/15**（规则顺序组是参照组，其余 4 组 12/12）；
- 流水线 8/10、13/15，差额是件级字段（T04/T05）；
- 简单组 19/20，金额 10/10。

**记住**：Task 9 让退款评测从“10 条能跑”变成“有 dev/held-out、有 CI、有分类”。

## 五、任务之间的关系

### 1. 三条线

| 线 | 任务 | 作用 |
|---|---|---|
| 样本线 | 1 → 9 | 先有普通样本，再有困难样本 |
| 执行线 | 2 → 3 / 4 → 5 | 快回路 + 慢回路 |
| 结论线 | 6 → 7 → 8 → 10 | 基线 → 修复 → 校准 → 验收 |

### 2. 两条回路

| 回路 | 工具 | 特点 | 什么时候跑 |
|---|---|---|---|
| 快回路 | `eval_e2e.py` | 确定性、无 judge、几十秒 | 每次改代码 |
| 慢回路 | EvalFlow | judge 质量分、有方差 | 阶段验收、版本对比 |

Task 9 的 B07 gold 冲突，就是快回路抓出来的。

### 3. 测量成熟度

- Task 1：先有样本；
- Task 6：先有数；
- Task 7：知道数会抖；
- Task 8：只用不抖的指标调阈值；
- Task 9：给退款加 CI、分 dev/held-out；
- Task 10：把“哪些数能信”写进验收。

## 六、关键术语小抄

| 术语 | 白话 |
|---|---|
| hit@3 | 正确答案所在资料块，有没有出现在前 3 条 |
| MRR | 正确答案排得越靠前越高；排第 1 是 1，排第 5 是 0.2 |
| context_precision | 检索回来的资料里，有多少是真正相关的 |
| context_recall | 应该找到的资料，找到了多少 |
| faithfulness | 回答里的说法，是否都能在检索资料里找到依据 |
| answer_relevance | 回答是否切题（通用 judge 对“转人工/拒答”容易误判） |
| 误拦率 | 该放行的被拦住 / 可答题总数 |
| 误放率 | 该拦住的被放行 / 负样本总数 |
| dev / held-out | dev 可参与调参；held-out 只做验证 |
| Wilson CI | 用样本量反推真实准确率的可信范围；n 越小越宽 |
| judge 方差 | 同一个回答，judge 两次打分可能不同 |
| 质量传导 2×2 | 检索好坏有没有传到最终答案上 |
| fail-closed | 拿不准时按“拦住/转人工”处理，而不是放行 |

## 十、常见困惑

**Q：为什么 44 条不用 385 条？**
385 是外部模型生成的 query 池，没有 gold；44 是人工审核、能判对错的样本。全量 385 条需要大量标注，不适合当前阶段。

**Q：为什么 relevance 提升不能算 FAQ 的功劳？**
同批重复 3 次，relevance 极差 3.86pp；0.8614 → 0.9045 落在噪声带内。correctness / recall 的提升才超出噪声。

**Q：为什么流水线低于模型？**
`compliance` 的规则：模型和规则都有结论但不一致 → 转人工。T04/T05 是模型判对、规则按整单字段判错，所以流水线被升级成人工。这是安全网的代价，不是模型错。

**Q：为什么 held-out 不叫盲测？**
运行后修正过 T01/T03 的 gold（与 B07 冲突），而且修改 prompt 前已经看过一次结果。它现在是 held-out 验证，不是严格盲测。

**Q：为什么既有 run-local 又有 run-NN？**
`run-local` 是确定性脚本，只看路由/金额/动作；`run-NN` 是 EvalFlow，含 judge 质量分。两者不能互相替代。

**Q：为什么阈值不升到 0.58？**
0.58 能拦住「能分期付款吗」，但会误拦合法的「FB-30 保修多久」。语义闸已经把双零区间扩到 0.53–0.56，0.55 两侧都有余量。

**Q：为什么还要语义闸，机械阈值不够吗？**
机械闸只看 top1 相似度，分不开“话题近”和“有答案”。语义闸只处理边界带，成本可控，解决了 0.55 附近的漏放/误杀。

## 十一、三句话总结

1. Ch07 不是做功能，是给系统装一套**可复现、可解释、能回归**的评测设备。
2. 它产出了三样东西：**基准样本与脚本**、**关键决策（dense / 0.55 / 语义闸）**、**已知边界**。
3. 它最大的价值不是分数，而是让你知道**哪些分数能信、哪些不能**。
