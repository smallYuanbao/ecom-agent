# Ch03 设计：C 出口（退款 8 状态流水线）

> 实施计划：[ch03-rules-exit.md](../plans/ch03-rules-exit.md)
> 规则来源：[电商客服-规则表.md](../../design/电商客服-规则表.md)
> 依据：D1 = C（8 状态）、D2 = B（高风险守卫）、D3 = A（独立 need_info）、D8 = B（结构化出参）

## 目标

把 `rules` 出口从占位换成真实的退款流水线：**金额由代码算，合规必须跑，模型只负责读懂和复述**。

**范围只做退款**。价保 / 订单变更识别后直接转人工（理由见「本章不做」）。

验收标准：

1. 8 个状态都能走到（每个状态至少一条测试路径）
2. 15 条转移各有测试，7 条守卫各有正反用例
3. **手算 10 份合同，金额 10/10 一致**
4. 规则表的 10 条判定各有正反用例
5. 缺 `order_id` → 列出用户最近订单让用户点选（不是追问文字）
6. 触红线 → 转人工，**不经过 respond**
7. 回答里的金额必须**逐字等于** `compute` 的输出
8. 每个状态落一行 `trace_span`

## 技术栈

沿用 Ch01/Ch02：LangGraph 子图、async SQLAlchemy、openai SDK。**本章不引入新依赖。**

## 架构

```
主图 classify_intent → route=rules → rules 节点（子图）
                                            │
   ┌────────────────────────────────────────┴──────────────┐
   │  8 状态子图                                            │
   │                                                        │
   │  intake ──► extract ──► validate ──► query_data        │
   │    │           │          │  ▲           │  ▲          │
   │    │           │          │  └─ need_info┘  │          │
   │    │           │          └─────────────────┘          │
   │    │           │                                        │
   │    │           └──(2 次失败)──► 转人工                  │
   │    └──(缺必填)──► need_info                             │
   │                          query_data ──► compute        │
   │                                            │           │
   │                                       compliance       │
   │                                        │      │        │
```

**模型只在两个节点出现**：`extract`（抽取要素）和 `respond`（组织语言）。
`validate / query_data / compute / compliance` 全是代码。

## 状态与转移

8 状态 / 15 转移 / 7 守卫（照 D1，逐条实现逐条测试）：

| # | 当前 | 条件 | 下一 | 类型 |
|---|---|---|---|---|
| 1 | intake | 必填齐全 | extract | 守卫 |
| 2 | intake | 缺必填 | need_info | 守卫 |
| 3 | extract | 抽取完成 | validate | 无条件 |
| 4 | validate | 要素齐全且一致 | query_data | 守卫 |
| 5 | validate | 缺失 / 矛盾 | need_info | 守卫 |
| 6 | validate | 重试 2 次仍失败 | 转人工 | 守卫 |
| 7 | need_info | 用户补充完整 | validate | 无条件 |
| 8 | need_info | 用户放弃 / 超时 | 结束 | 守卫 |
| 9 | query_data | 查到数据 | compute | 守卫 |
| 10 | query_data | 查不到（无记录） | need_info | 守卫 |
| 11 | query_data | 工具超时/异常（重试后） | 转人工 | 守卫 |
| 12 | compute | 总是 | compliance | 无条件 |
| 13 | compliance | 未触红线 | respond | 守卫 |
| 14 | compliance | 触红线 | 转人工 | 守卫 |
| 15 | respond | 总是 | 结束 | 无条件 |

**第 10 条与第 2、5 条话术要区分**：前两条是"用户没给"，第 10 条是"系统没查到"。

## 各节点契约

### intake（代码）

| 项 | 内容 |
|---|---|
| 读 | `resolved_query` / `raw_query`、`conversation_id` |
| 写 | `order_id`（能从原句抽到就抽）、`draft` |
| 逻辑 | 正则抽 4 位以上数字当订单号；**不做业务校验**（那是 validate 的事） |
| 失败 | 抽不到 → `need_info`（带上"列出候选"的意图） |

**为什么 intake 就抽订单号**：省一次 LLM 调用。订单号是纯数字，正则足够。

### need_info（代码 + 中断）

| 项 | 内容 |
|---|---|
| 读 | 缺什么、`conversation_id` |
| 写 | `pending_question`（写库，跨轮恢复靠它）、`answer`（追问话术） |
| 逻辑 | 缺 `order_id` → **`list_user_orders` 列出最近 3 单，`interrupt` 让用户点选**；缺退款原因 → 文本追问 |
| 失败 | 用户放弃/超时 → 结束 |

参考实现的这条做法值得抄：**缺单号不追问文字，直接给可选项**。同样能顺带完成归属校验。

### extract（模型）

| 项 | 内容 |
|---|---|
| 读 | `resolved_query` |
| 写 | `draft`：`{order_id?, reason_code?, item_count?, condition_ok?}` |
| 逻辑 | `structured_call` 抽四个字段；抽不到就是缺 |
| 失败 | 格式错误 → 重试 1 次；仍失败 → `validate` 判缺失（不是直接转人工） |

**`condition_ok` 是三态**：`true` / `false` / `null`。模型拿不准时必须给 `null`，不要猜。

### validate（代码）

| 项 | 内容 |
|---|---|
| 读 | `draft` |
| 写 | 校验结果 |
| 逻辑 | ① 必填齐全（`order_id`、`reason_code`）② 订单存在且属于本人 ③ 日期不矛盾（签收不早于发货）④ `condition_ok` 为 `null` → 视为"需人工判断" |
| 失败 | 缺失/矛盾 → `need_info`；`condition_ok=null` → **转人工**（fail-closed） |

### query_data（代码）

| 项 | 内容 |
|---|---|
| 读 | `order_id`、`user_id` |
| 写 | `order_snapshot`：状态、实付、件数、下单/发货/签收时间 |
| 逻辑 | `repo_order.get_order(order_id, user_id=...)`；归属校验在这层（S1） |
| 失败 | `NotFound` → `need_info`（引导补单号）；超时/异常 → 转人工 |

**归属校验必须在 code 里**：这个子图不经过工具层，工具那道校验够不着（参考实现踩过）。

### compute（纯函数，**模型不参与**）

```python
def compute_refund(order: OrderSnapshot, request: RefundRequest) -> RefundResult
```

| 项 | 内容 |
|---|---|
| 输入 | 订单快照（状态/实付/件数/签收时间）+ 退款请求（原因/件数/完好） |
| 输出 | `{eligible, refund_amount, reason_code, breakdown}` |
| 约束 | **无 IO、无随机、无时间依赖**（当前时间由调用方传入） |

金额公式（详见规则表 §4）：

```
退款金额 = floor(实付 × 退货件数 / 总件数)
```

运费不参与计算（`amount` 本身就是商品实付）。

**"当前时间由调用方传入"** 是为了可测：`compute` 不读 `datetime.now()`，否则测试结果依赖运行日期。

### compliance（代码，硬闸）

按顺序检查，任一命中 → 转人工：

| # | 红线 | 来源 |
|---|---|---|
| 1 | 退款金额 > 订单实付 | 逻辑不可能，出现即 bug |
| 2 | 退款金额 ≤ 0（可退但算出来是 0） | 同上 |
| 3 | 商品属于法定不适用类，但 `eligible=true` | 规则冲突 |
| 4 | 签收超 7 天且原因为"无理由"，但 `eligible=true` | 规则冲突 |

**第 3、4 条是"交叉校验"**：`compute` 已经判过一次，`compliance` 再独立判一次。
两次不一致说明有 bug —— **宁可转人工，不可放行**。

### respond（模型）

| 项 | 内容 |
|---|---|
| 读 | `compute` 的结构化结果、`citations` |
| 写 | `answer` |
| 约束 | **只能复述金额，不能计算**；金额必须逐字出现在提示里 |

prompt 里给出算好的数字，要求"直接引用这个数字，不要自己算"。
Ch06 会加输出校验兜底（金额必须等于 `compute` 输出）。

## 数据变更（阻塞项）

| # | 表 | 字段 | 用途 |
|---|---|---|---|
| 1 | `orders` | `signed_at DATETIME NULL` | 7 天窗口判定（法规：自签收次日起算） |
| 2 | `orders` | `quantity INTEGER NOT NULL DEFAULT 1` | 部分退款按件均摊 |

三处要同步改：`schema.sql`、`models.py`、`seed.py`（给已签收单填 `signed_at`、件数 1–2）。
`init_db.py` 的自动比对会拦住漂移。

**`signed_at` 允许为空**：未签收的单本来就没有值。判定时 `NULL` → 按"未签收"处理（第 5 条规则）。

## 与语料的一致性约束

C 出口的每条判定都必须能在 `data/kb/` 找到依据（或明确标注"自定"）：

| 规则 | 语料依据 |
|---|---|
| 7 天自签收次日 | regulations art-010 |
| 不适用商品四类 | art-006 |
| 完好/不完好判定 | art-008 + returns.md |
| 退货运费承担 | returns.md |
| 部分退款券不退 | promo.md |

**冲突的处理**：以语料为准，改代码。因为语料是给用户看的、会被引用进答案——
代码和语料打架，用户会拿两句话对质。

## 判定方式：本章用代码（附待评估项）

本章按 **规则表判定**（方案 A）实现，理由：

- 金额与一致性要求最高的部分
- 判定结果可逐条对拍、可审计
- 规则表已覆盖主要情形

**待评估（不在本章范围）**：让模型判定资格、代码只算金额（方案 C）。
评估方式：**20–30 单 gold set（人工标 可退/不可退/转人工），对比规则判定与模型判定的准确率与误判方向**。
触发条件：规则表维护成本明显上升，或评测显示规则漏判率高。

## 测试与验证

| # | 测试 | 断言 |
|---|---|---|
| 1 | 状态可达性 | 8 个状态各有至少一条路径能走到 |
| 2 | 转移表 | 15 条转移逐条测；7 条守卫各有正反用例 |
| 3 | **手算对拍** | `data/eval/refund_10.json` 十份合同，金额 10/10 一致 |
| 4 | 规则判定 | 规则表 10 条各有正反用例 |
| 5 | 缺 order_id | 返回候选列表 + `interrupt`，不是纯文本追问 |
| 6 | 触红线 | 走转人工，`respond` 未被调用 |
| 7 | 金额一致 | `respond` 的文本里出现的金额 === `compute` 输出 |
| 8 | 越权 | 查别人的单 → `NotFound` → need_info，不泄露"这单存在" |
| 9 | trace | 每个状态一行 span，共享 trace_id |

**手算 10 份合同**的构造原则：覆盖 10 条规则各一次，加 2–3 个边界（刚好 7 天、刚好超期 1 天、2 件退 1 件）。

## 本章不做

| 不做 | 归属 |
|---|---|
| 价保 / 订单变更（识别后转人工） | 后续（语料里还没有这两类政策） |
| 图内持久化恢复（park / checkpointer） | Ch05 |
| 输出校验（金额/措辞机械校验） | Ch06 |
| 并发锁、超时清理 | Ch05 |
| 模型判定资格（方案 C） | 待评估，见上 |

### 价保 / 变更为什么不做

语料里**没有这两类政策**（returns.md 只写了一句「价保规则见另一份政策」，那份政策不存在）。
凭空编规则的话：语料和代码没法对齐，面试被问"这条规则哪来的"也答不上。

**当前行为**：识别为这两类意图 → 直接转人工，并在落池里标记 `source=rule_not_implemented`。

## 关键决策记录

| 决策 | 选择 | 备选与理由 |
|---|---|---|
| 章范围 | **只做退款** | 三个都做：价保/变更无语料依据，编出来的规则经不起问 |
| 判定方式 | **代码（规则表）** | 模型判定：可测但一致性差；记为待评估（20 单 gold 对比） |
| 金额是否告知用户 | **报**（`respond` 复述） | 不报：用户问的就是金额，不报等于答非所问；且失去唯一可对拍的指标 |
| 运费 | **不进退款计算** | 计入：`amount` 本身是商品实付，加运费要连带改下单流程 |
| `condition_ok` 拿不准 | **转人工（fail-closed）** | 放行：判断不了就放行等于放弃 C 出口的意义 |
| 缺 order_id | **列候选让用户点** | 文本追问：体验差，且要在下一轮再解析一次 |
| 未签收的 `signed_at` | **NULL → 按未签收处理** | 填默认值：会让 7 天窗口算错 |
