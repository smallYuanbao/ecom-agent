## 划章原则：分层实现，功能验收

**为什么不是按功能划章**：横切关注点（日志/错误码/安全）无处安放、schema 被迫提前、同一批文件反复重写。
详见讨论结论：按层实现能保证依赖清晰，按功能验收能保证每章可演示。

**做法：行走骨架（walking skeleton）**

```
Ch02 结束时：
  /api/chat → 主图 → 意图分流 → 出口
                              ├─ A 知识   真实
                              ├─ B 数据   占位（明确告知"开发中"）
                              ├─ C 规则   占位
                              ├─ D 转人工 真实（话术+建单，简单）
                              └─ E 兜底   真实（三脚本，最简单）
```

**占位三原则**：

1. **明确告知，不假装成功**——绝不返回假金额
2. **统一节点，按 route 返回不同话术**
3. **契约先定**——占位与真实实现共用状态字段、错误码、trace；替换时只换函数，不动边与状态

**代价**：意图分类提前到 Ch02，边界规则要等 Ch03/Ch04 的真实出口跑起来后再调一轮——**这是预期内的返工，不是缺陷**。

## 每章的固定结构

```
## 目标（含验收标准）
## 技术栈（定死）
## 架构
## 目录结构
## 数据模型 / 核心逻辑
## 接口契约
## 测试与验证
## 本章不做
## 关键决策记录
```

**「本章不做」和「关键决策记录」是硬要求**——前者防止范围蔓延，后者是面试素材。
